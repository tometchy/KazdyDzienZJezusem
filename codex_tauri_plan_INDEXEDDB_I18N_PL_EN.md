# ZADANIE DLA CODEX: pełny PLAN migracji KażdyDzieńZJezusem do Tauri 2 + GitHub Pages

> **Wersja wymagań: 17 listopada 2026 — architektura bez backendu i pośredników OAuth; ujednolicony IndexedDB i obowiązkowe i18n.** GitHub Pages pozostaje statycznym, SEO-friendly WWW (read-only, jeżeli nie istnieje bezpieczny login bezserwerowy). Wersja Tauri używa GitHub REST API, nie Git CLI; publiczny SQLite FTS5 jest tylko odczytywany i wymieniany całym snapshotem, bez migracji runtime. Trwały **Outbox przechowuje TYLKO niewysłane zmiany/konflikty; po pewnym potwierdzeniu GitHub usuwa operację i pełny payload. Jeden IndexedDB Outbox w czystym JavaScript dla Tauri i ewentualnego WWW writable; NIE wprowadzaj osobnego pliku JSON ani drugiego adaptera, dopóki realny test nie wykaże konieczności.** Na Pixelu postmarketOS wykazano brak OPFS/SAH Pool, lecz **NIE** wykazano braku IndexedDB — przetestuj jego trwałość. GitHub `<login>/Notes` przechowuje czytelne Markdown `.md`, edytowalne też na GitHubie; potwierdzone treści mogą być tylko w RAM lub usuwalnym cache. **Wspólny frontend będzie od początku polsko-angielski (PL+EN), rozszerzalny na kolejne języki. Język UI nie ogranicza języka tekstów, przekładów, glos, gramatyki czy adnotacji.** Na bieżąco utrzymuj tłumaczenia UI, pomocy, SEO i metadanych Flathub/Google Play/App Store oraz screenshoty obu języków. Wymagane CodeceptJS (specyfikacje wykonywalne `I ...`, DSL, Protocol Drivers/Stubs i screenshoty), golden ZIP oraz test integralności 100% danych w <=60 s, GitHub Actions dla wszystkiego, Flathub/Flatpak na Linuksie i updater Tauri dla samodzielnych paczek.
>
> **KRYTYCZNY WARUNEK:** Nie proponuj żadnego procesu, endpointu, funkcji serverless, Cloudflare Worker, hostowanego brokera OAuth, zewnętrznego proxy lub serwera, który użytkownik musiałby wdrażać i utrzymywać, także „tylko do logowania”. Przy braku bezpiecznego, faktycznie obsługiwanego flow bez backendu wybierz **WWW read-only**. GitHub Actions są wyłącznie build/test/publish, nie usługą runtime ani kanałem przetwarzania prywatnych notatek.
>
> **UWAGA: TO JEST ZADANIE WYŁĄCZNIE ARCHITEKTONICZNE I PLANISTYCZNE.**
> Nie implementuj teraz migracji. Nie przepisuj ekranów, nie zmieniaj baz, nie usuwaj backendu ani POC, nie publikuj strony i nie wydawaj aplikacji. Zbadaj repozytorium, zweryfikuj ograniczenia, podejmij udokumentowane decyzje lub wskaż blokery i przygotuj kompletny, etapowy, wykonalny plan w **dokumentacyjnym pull request**. Bez merge.
>
> Ten dokument jest szczegółową specyfikacją zlecenia. Odpowiedzi typu „użyj Tauri i SQLite” albo zbiór ogólnych pomysłów nie realizują zadania.

## 1. Kontekst i cele

Repozytorium: **https://github.com/tometchy/KazdyDzienZJezusem**. Najpierw pobierz bieżący `origin/master`, przeczytaj `AGENTS.md`, `README.md`, katalogi `KazdyDzienZJezusem/`, `poc/`, `input/`, `input-raw/`, `tags/`, `scripts/`, istniejące testy oraz workflow w `.github/workflows/`. Zweryfikuj także status ostatnich PR i ich faktyczną zawartość: nie traktuj informacji poniżej jako gwarancji aktualności. Nie zakładaj, że ścieżki lub liczby dokumentów nie zmieniły się. W razie rozbieżności wykaż je w audycie.

**Obecny stan (potwierdzony w poprzednich eksperymentach):**

- Produkcja: ASP.NET Core MVC, Razor `.cshtml`, Unpoly do fragmentowej nawigacji, dane tekstowe w `input/`, publiczne tagi Markdown w `tags/`, Redis do części indeksów i sesji, GitHub jako źródło tagów, kontenery Podman i Cloudflare Tunnel. Obecne trasy obejmują `/Biblia`, `/Biblia/{translation}/{book}/{chapter}`, `/Biblia/Werset/{book}/{chapter}/{verse}`, `/Ojcowie`, `/Tagi`, `/Tag/{slug}`, `/login` oraz `/api/greek-interlinear` i `/api/tags/...`. Zbadaj je wszystkie, ich modele, zachowanie, UX i uprawnienia.
- POC: `poc/prepare.py`, `poc/build_sqlite.py`, `poc/frontend/`, SQLite FTS5 + WASM w przeglądarce. Indeks prebuilt ma ok. **115 317 rekordów, 33,36 MB** bez kompresji. Źródła w ostatnim teście: KJV 31 102, UBG 31 102, TNP 14 196, TR 7 957, Interlinear 7 940, Słownik 22 815, Ojcowie 205. TNP zawiera **47 ksiąg**, UBG i KJV 66; nie „naprawiaj” tego syntetycznymi danymi, zinwentaryzuj wersję źródła i zakres praw. Utrzymuj spójność językową i referencje źródeł.
- W testach Chromium na Pixelu 3a XL (postmarketOS) SAH Pool był szybszy od standardowego OPFS. W Tauri 2 na tym Pixelu WebKitGTK **nie udostępnia** `navigator.storage.getDirectory()` ani `createSyncAccessHandle`, więc WASM + SAH Pool **nie jest** podstawą natywnego wariantu. Natywne Rust + SQLite FTS5 z `rusqlite` działało offline na urządzeniu.
- Ostatni zakończony benchmark natywny na Pixelu (`kdzj-tauri-postmarketos-1794824516500.json`): 4/4 pomiary, zimny start samego przygotowania DB **758,715 ms**, trzy ciepłe **67,643 / 63,642 / 67,295 ms** (mediana **67,295 ms**), typowe SQL p50 ciepłe **0,122 ms**; identyczne liczby trafień. To **nie** jest czas otwarcia całej aplikacji ani koszt pełnej komunikacji JS–Rust. SQLite 3.50.2, 115 317 rekordów.
- Istniejący build Tauri w `poc/frontend/src-tauri`, workflow `.github/workflows/tauri-postmarketos.yml` i statyczny workflow `.github/workflows/poc-pages.yml` stanowią materiał wejściowy. Zbadaj ich rzeczywiste ograniczenia. Build dla Pixela to **Linux AArch64/musl z Alpine**, nie APK Androida.
- Ważne komponenty do zachowania semantycznie: porównywanie przekładów, nawigacja po wersetach, odnośniki i deep-linki, fragmenty biblijne, pisma ojców, tagi, interlinear grecko-polski, Strong, gramatyka, pomocne tooltipy i modal szczegółów, źródła i licencje. Badaj faktyczną funkcjonalność `Controllers`, `Services`, `Views`, `wwwroot/js/greek-interlinear.js`, a nie tylko wyliczenie katalogów.

**Najważniejsze decyzje o danych i językach:** prywatne repo GitHub `Notes` zawiera wyłącznie zwykłe pliki Markdown dla notatek. **Jedyny trwały magazyn zmian niepotwierdzonych na urządzeniu to IndexedDB** (`pending_changes`), zarówno w Tauri (WebView), jak i w przyszłej edytowalnej stronie WWW. Ma przeżyć restart, odłączenie sieci i aktualizację aplikacji; **potwierdzone przez GitHub operacje/payloady są usuwane**. Zdalne, potwierdzone notatki nie są kopiowane na stałe do Outboxa; mogą istnieć w RAM lub wymienialnym cache SQLite. Publiczny SQLite, generowany przez Actions, jest wymienialnym snapshotem bez runtime migracji. Wymagaj empirycznego dowodu trwałości IndexedDB na wszystkich docelowych WebView i wielu oknach (Pixel WebKitGTK, Linux/Flatpak, Windows WebView2, Android/iOS); nie dopisuj bez dowodu drugiego pliku jako obejścia. **Od pierwszego wdrożenia UI działa po polsku i angielsku**, katalogi tłumaczeń są przygotowane na kolejne języki, a język interfejsu i warstwy językowe treści działają niezależnie.

**Docelowa wizja:** **jedno rozwiązanie Tauri 2, jeden frontend HTML/CSS/JavaScript i jedna wspólna logika domenowa**, udostępnione jako statyczna, dobrze indeksowalna strona na **GitHub Pages** oraz natywne pakiety **Tauri 2**. **Nie buduj dwóch UI.** Obie wersje oferują publiczne treści, nawigację, wyszukiwanie i Unpoly. **Wersja natywna musi mieć „Zaloguj przez GitHub” bez PAT**, przeprowadzać użytkownika przez autoryzację i automatycznie odnajdywać/zakładać **dokładnie jedno prywatne repo `Notes`** na jego osobistym koncie. Notatki są local-first i synchronizowane przez **GitHub REST API**; osoby z aktualnym prawem write do publicznego repo aplikacji edytują też wybrane wspólne dane. Przyznawanie/cofanie prawa odbywa się w samym GitHubie. **WWW może mieć te same funkcje zapisu wyłącznie w przypadku udokumentowanej, bezpiecznej i realnie działającej autoryzacji bez żadnego pośrednika**. Jeżeli to nie jest wykonalne, **WWW ma być trwale dopuszczalnym produkcyjnym wariantem read-only ukierunkowanym na SEO**: bez udawanego logowania, bez sekretów i bez skrytego serwera. Jest to **z góry zatwierdzony fallback**, a nie blocker migracji. W obu przypadkach GitHub Pages publikuje tylko statyczne pliki; nie istnieje nasz własny runtime backend, Cloudflare Worker ani funkcja serverless. Natywna aplikacja działa offline. Po finalnej migracji usuń osobne UI POC oraz niepotrzebny ASP.NET Core/Redis/Compose/Cloudflare runtime, ale dopiero po sprawdzeniu parytetu i zaplanowaniu rollbacku.

## 3. Wymagania nienegocjowalne co do technologii i prostoty

1. **Frontend wyłącznie w JavaScript (ES Modules), HTML i CSS. Żadnego TypeScriptu** w kodzie aplikacji ani testach. Przyszłe konfigi i przykłady CodeceptJS również `.js`. Nie migruj do React, Vue, Svelte, Angular, Next/Nuxt ani innego frameworka komponentowego. Dopuszczalny jest obecny prosty build Vite i natywne `template`, DOM APIs, Web Components **tylko jeśli faktycznie upraszczają**. Nie wprowadzaj generowania skomplikowanych warstw kodu.
2. **Tauri 2** pozostaje jednym frameworkiem natywnym. Rust to wyłącznie konieczna natywna warstwa Tauri/SQLite/systemowa; brak kopiowania UI, reguł nawigacji lub logiki biznesowej z JS do Rust. Nie wracaj do MAUI, Avalonia, Uno, OpenMaui.
3. **SQLite wyłącznie jako odtwarzalny, kanoniczny lokalny snapshot treści publicznych** (wersety, Ojcowie, słownik, interlinear, publiczne tagi i FTS), budowany przez GitHub Actions i podczas aktualizacji wymieniany W CAŁOŚCI. Nie umieszczaj w nim prywatnych notatek ani niewysłanych tagów. **JEDEN trwały IndexedDB Outbox w czystym JS, zarówno dla Tauri WebView, jak i dla ewentualnego WWW writable**, z elastycznymi obiektami operacji JSON w `pending_changes`. **Nie twórz osobnego `outbox.json` i nie uzależniaj Outboxa od Rust** tylko dlatego, że działa w Tauri. IndexedDB nie jest OPFS/SQLite WASM; brak OPFS na Pixelu nie dowodzi braku IndexedDB. Istotne próby trwałości i współbieżności na realnych targetach są opisane w § 5.1. WWW read-only nie tworzy prywatnych operacji. Nie używaj `window.localStorage` jako jedynej kopii niewysłanych danych. Drobne preferencje UI można trzymać w osobnym object store tego SAMEGO IndexedDB, bez mieszania ich z Outboxem. To nie tworzy drugiej logiki aplikacji ani drugiego prywatnego magazynu.
4. **Jedna logika domenowa JS**: kontrakty repozytorium danych, reguły referencji i adresów, walidacja, prezentacja wersetów, rozpoznawanie gramatyki, mapowanie ksiąg, polityki uprawnień UI, notatki i synchronizacja. Sprawy SQL realizuj przez wspólne, jawne kontrakty operacji i testy kontraktowe; nie dawaj UI arbitralnego `executeSql(sql)` ani możliwości wstrzyknięcia SQL.
5. **Mała i płaska struktura katalogów**, bez „enterprise clean architecture” po kilkanaście plików na ekran, bez wzorców i abstrakcji pozbawionych realnych korzyści. Dokumentuj regułę: nowy folder/adapter tylko wtedy, gdy rozdziela rzeczywiste środowisko, odpowiedzialność albo punkt wymiany technologii.
6. **Żadnego odświeżania całej strony podczas normalnej nawigacji.** Każdy ekran, karta, modal i wyszukiwanie odświeża tylko właściwy fragment. Zachowaj **Unpoly**, o ile zadziała z HTML lokalnie wyrenderowanym z danych SQLite (oficjalne `up.render({ content/fragment/document })`, `up.navigate`, `up.layer`, `[up-keep]`). Unpoly nie musi pobierać HTML z ASP.NET. Jeżeli znajdziesz obiektywny bloker, przedstaw minimalny zamiennik bazujący na natywnym DOM + History API, bez innego frameworka; pokaż dowód, pomiar i plan przejścia. XHTML **nie** jest biblioteką nawigacji (nie mylić z htmx). Unikaj wstrzykiwania niezsanityzowanego HTML.
7. URL-e i deep-linki muszą działać. **Wersja WWW ma być naprawdę SEO-friendly bez wykonywania JavaScript**: zaplanuj generowanie na CI statycznych, indexowalnych HTML dla publicznych tras (minimum: start, przekłady, księgi, rozdziały, **każdy istniejący werset jako osobna kanoniczna strona porównawcza**, Ojcowie, tagi, słownik w zakresie zgodnym z licencjami i budżetem GitHub Pages). W HTML mają być od razu treść, `title`, opis, odpowiednie linki, canonical, metadane języka, sitemap/robots; nie tylko pusty `div` i `fetch` bazy. **Nie wybieraj hash routingu jako jedynej nawigacji dla stron indeksowanych przez wyszukiwarki**. Normalna nawigacja po uruchomieniu JS ma nadal używać Unpoly i wymieniać wyłącznie właściwe fragmenty. Weryfikuj realne bezpośrednie URL-e, refresh i 404 bez SPA fallback GitHub Pages, poprawność statycznego `base`, identyczne URL-e w Tauri tam, gdzie wykonalne, oraz migrację starych linków. Każda karta ma własny werset, stan i historię.
8. **Dwujęzyczność od początku:** pełne PL/EN UI, komunikaty błędów, pomoc, powiadomienia, nawigacja, daty/liczby, dostępność oraz metadane/sklepowe screenshoty; aktualizuj obie wersje przy każdej zmianie funkcji, nie „później”. UI locale to osobna preferencja, niezależna od warstw przekładów/adnotacji w czytniku. Szczegóły i akceptacja w § 5.2.
9. Po **zakończonej** migracji usuń `poc/` i wszystkie środowiska testów POC oraz zbędny ASP.NET/Redis/Compose/Cloudflare z runtime, o ile nie obsługują już potrzebnej funkcji. Zachowaj potrzebne generatory danych, testy regresyjne i historyczne dowody w odpowiednio nazwanych docelowych katalogach; nigdy nie usuwaj źródeł, licencji, tagów czy historii Git.

## 5. Model danych: jedna treść, różne silniki storage

Przygotuj schemat kanoniczny obejmujący **nie tylko** obecną tabelę wyszukiwarki `docs_fts(source, ref, pl, gr, en, lemma)`, która nadaje się do fulltextu, lecz również normalizowane dane do szybkiego wyświetlania: księga/rozdział/werset/źródło, porównanie przekładów, pisma ojców, tagi/ranges, słownik grecki i polski, kody Strong, kody gramatyczne, formy odmienione, lemmy, alternatywy, pochodzenie danych i licencje. Zachowaj wszystkie istniejące zachowania, szczególnie logikę dokładnych form i kontekstu z `GreekInterlinearService`/`GreekDictionaryRepository`; **nie zastępuj dokładnej analizy gramatycznej samym FTS**. Udokumentuj normalizację greki (przydechy, akcenty, sigma końcowa, kontekst), bo obecny POC FTS normalizuje wyszukiwanie inaczej niż repozytorium interlinear; zaplanuj testy wykrywające utratę informacji.

**GitHub jest wyłącznie zdalnym repozytorium danych, a nie wymaganym serwerem tej aplikacji.** W przeciwieństwie do obecnego kontenera nie wolno używać lokalnego `git`, `git clone/fetch/commit/push`, SSH agentów ani wywoływać tych komend przez Rust/Tauri dla zwykłego użytkownika. **Warstwa synchronizacji działa w JavaScript i korzysta z GitHub REST API**, z wąskim adapterem transportu HTTP dla Tauri tam, gdzie WebView narzuca CORS. Zasady edycji, rozwiązywania konfliktów i struktur danych są wspólne. Git w GitHub Actions do checkoutu/commitów CI oczywiście pozostaje dozwolony; zakaz dotyczy runtime aplikacji i synchronizacji notatek/tagów. Szczegółowa mapa migracji Git CLI → GitHub API znajduje się w § 7.6.

**Adapter JS:** operacje typu `getTranslations`, `getBooks`, `getChapter`, `getVerseComparison`, `getFathersChapter`, `search`, `getTagsForFragment`, `getGreekAnnotations`, `getGrammarHelp`, `getNote`, `saveNote`, `sync`, `getDataVersion` (to przykłady, sprawdź rzeczywiste potrzeby). Wszystkie zwracają spójne obiekty/Promise i te same błędy; `views/` nie wie, czy publiczne dane SQLite pochodzą z WASM/OPFS czy z natywnego Rust. **Publiczne SQLite jest tylko do odczytu i w 100% odtwarzalne**, a użytkownik edytuje wspólne dane przez GitHub REST API i trzyma **wyłącznie niepotwierdzone operacje** w **tym samym IndexedDB Outboxie** w Tauri oraz potencjalnym writable WWW. Notatki po stronie zdalnej to pliki Markdown w `<login>/Notes`. Nie mieszaj niesynchronizowanego stanu z wymienialną bazą SQLite; nie utrzymuj dwóch formatów notatek ani dwóch logik synchronizacji.

**Browser:** jedna wstępnie zbudowana baza SQLite i indeks na urządzeniu (preferowany `opfs-sahpool`, jeśli obsługiwany) z pobieraniem gzip, manifestem, SHA-256, wersjonowaniem schematu i trwałym magazynem publicznej treści. Sprawdź Firefox, Chromium i WebKit/Safari; przy braku OPFS/SAH Pool zaplanuj publiczny, read-only odczyt z WASM w pamięci. **IndexedDB jest osobną funkcją przeglądarki i ma służyć Outboxowi**, jeśli WWW otrzyma w przyszłości bezserwerowy login; nie zakładaj, że wymaga OPFS. WWW read-only nie wymaga prywatnego Outboxa.

**Tauri:** natywne SQLite FTS5 w Rust tylko dla publicznego snapshotu. Tauri na Pixelu z WebKitGTK NIE ma OPFS/SAH Pool (potwierdzone benchmarkiem), ale to nie oznacza, że `indexedDB` jest niedostępne. **Używaj tej samej JS implementacji IndexedDB Outbox co WWW**; do notatek, kolejek i konfliktów NIE dopisuj Tauri FileStore ani Rust CRUD. Wąski transport HTTP/sekretów może być natywny, a publiczne zapytania SQL przechodzą przez `invoke`. Sprawdź dokładnie, jak Tauri identyfikuje i przechowuje profil WebView, w tym `identifier`, Windows/Android `useHttpsScheme`, `dataDirectory`, origin, sandbox Flathub i zachowanie różnych okien/instancji. **Wszystkie okna jednego konta muszą w praktyce widzieć ten sam IndexedDB, a po aktualizacji musi on mieć tę samą lokalizację**; nie uznawaj tego bez pomiaru. Gdy test ujawni brak współdzielenia lub trwałości na konkretnej platformie, przedstaw dowody i minimalną alternatywę do osobnego zatwierdzenia przez właściciela; NIE wdrażaj automatycznie dwóch magazynów i nie deklaruj funkcji offline jako działającej. Waliduj SQL/parametryzuj zapytania, podpisy i capabilities.

### 5.1. Publiczne SQLite + JEDEN IndexedDB Outbox na każdej platformie — bez migracji SQL

**Źródła prawdy i trwałość:**

| Rodzaj danych | Gdzie istnieją | Co dzieje się po aktualizacji lub sync |
| --- | --- | --- |
| Biblia, interlinear, słownik, Ojcowie, tagi opublikowane | `content.sqlite3` wygenerowane przez CI | Publiczny snapshot jest weryfikowany i w całości podmieniany, bez migracji w runtime |
| Potwierdzone prywatne notatki | GitHub `<login>/Notes` — zwykłe pliki Markdown `.md` | GitHub jest źródłem prawdy; do czytania RAM lub **usuwalny**, oddzielny cache (może być SQLite) |
| **Niewysłane** notatki/tagi i konflikty | **IndexedDB `pending_changes`** we wspólnej implementacji JS w **Tauri i WWW writable** | Trwałe do chwili potwierdzenia na GitHubie / rozwiązania konfliktu, nigdy nie podmieniane razem z bazą publiczną |
| Małe ustawienia, np. język UI i wybrane warstwy językowe | **Ten sam IndexedDB**, ale odrębny mały object store `preferences` (ewentualnie świadomie inny lekki mechanizm, jeśli nie utrudnia utrzymania) | Przeżywają restart, nie są mieszane z `pending_changes`; nie zawierają prywatnych treści |
| Tokeny / refresh tokeny GitHub | Bezpieczny mechanizm poświadczeń OS/wąska warstwa Tauri | **Nigdy** IndexedDB, Outbox, publiczne SQLite, strona Pages ani logi |

**Żadnego `outbox.json` w Tauri, żadnego adaptera plikowego i żadnego natywnego odpowiednika Outboxa** jako domyślnej architektury. Nie utrzymuj trzech schematów/formatów notatek. Jeden `IndexedDbOutbox` w JavaScript działa w Tauri/WebKitGTK, Tauri/WebView2, Android/iOS WebView oraz ewentualnym WWW writable; tylko inicjalizacja środowiska i autoryzacja mogą się różnić. Read-only WWW nie inicjalizuje `pending_changes` ani nie pozwala na zapis. Zapis drobnych `preferences` w tym samym IDB nie zmienia reguły, że **Outbox zawiera wyłącznie operacje niepotwierdzone**.

**Jeden kontrakt i elastyczny format:** `enqueue()`, `getPending()`, `updatePending()`, `removeAcknowledged()`, `getConflicts()`, `acquireSyncLease()`. Każda operacja jest obiektem JSON z ID UUID, `accountId` (numeryczne ID GitHub), rodzajem `note-upsert` / `note-delete` / `public-tag-update`, ścieżką repo + pliku, pełną zawartością Markdown lub walidowaną zmianą taga, `baseSha`, stanem `pending`/`conflict`, datą i licznikiem prób. Dodawanie pól do JSON nie może wymagać migracji SQL. Nie zapisuj tokenów ani całej zsynchronizowanej biblioteki notatek do Outboxa. Wpisy `conflict` pozostają tak długo, jak użytkownik nie rozwiąże konfliktu i nie otrzyma potwierdzenia. Stosuj izolację kont (np. klucz `{accountId,operationId}`); nigdy nie pokazuj notatek konta A na koncie B.

**Wymóg trwałości:** nie raportuj „Zapisano lokalnie”, zanim transakcja IndexedDB (`readwrite`) nie zostanie **ukończona**, a nie tylko zainicjowana. Zwróć uwagę na semantykę `commit`, `oncomplete`, różnice `durability: 'strict'`, limity pamięci, evictions, tryb incognito, `QuotaExceededError`, zdarzenia `blocked` i `versionchange`. Dla WWW writable żądaj `navigator.storage.persist()` tam, gdzie działa; dokumentuj brak gwarancji, gdy użytkownik czyści dane witryny lub przeglądarka usuwa magazyn. Zaprojektuj eksport niepotwierdzonych zmian (np. JSON/Markdown) i stan alarmowy, gdy zapis nie jest trwały. W Tauri konieczne testy, czy WebView utrzymuje IndexedDB po zamknięciu procesu, aktualizacji aplikacji, aktualizacji WebKitGTK/WebView2, zmianie wersji Flatpaka, restarcie OS i na rzeczywistym Pixelu. **Brak OPFS nie jest argumentem przeciw IndexedDB, ale nie wolno go przyjąć za potwierdzony bez testu.**

**Wiele kart / okien / instancji:** w WWW otwórz przynajmniej 3 karty tej samej origin; zapis do IDB ma być transakcyjny, a synchronizację obsługuje pojedynczy aktywny klient na konto przez `navigator.locks` (jeżeli jest) lub poprawny lease z fencing token/generation w SAMEJ IDB. **Nie blokuj transakcji IndexedDB na czas połączenia sieciowego**. Wszystkie okna Tauri muszą odczytywać dokładnie ten sam outbox: sprawdź domyślne WebView `dataDirectory` i origin, bo ich rozbieżność może spowodować osobne bazy dla różnych okien. Jeśli to się zdarza, zaprojektuj **wspólną konfigurację profilu WebView dla okien**; nie „naprawiaj” tego przez drugi store. Oceń i przetestuj równoległe procesy/instancje, a nie tylko karty w jednym procesie; w razie braku gwarancji przedstaw warunek blokujący/fallback do zatwierdzenia. BroadcastChannel służy tylko do powiadomień, nie do gwarantowanego mutexu.

**Synchronizacja GitHub REST API:** każdy lokalny zapis pełnego Markdown `notes/<id>.md` (lub tagu) trafia najpierw do Outboxa. Po odzyskaniu internetu aplikacja odczytuje kolejkę, przy podstawie `baseSha` ustala aktualną zdalną wersję, wykonuje warunkowy zapis i potwierdza SHA/commit. Dopiero po jednoznacznym potwierdzeniu, także przez odczyt z GitHuba po utraconej odpowiedzi, usuwa trwale z IndexedDB operację i jej tekst. Przy 401/403/409/422/429, wyłączeniu sieci lub konflikcie pozostawia pełną treść i pokazuje stan. Wylogowanie, zmiana konta, update lub wyczyszczenie publicznego cache nie mogą samodzielnie usunąć kolejki. Nie gwarantuj synchronizacji przy zamkniętej aplikacji — wymagane wznowienie po jej uruchomieniu albo odzyskaniu połączenia, z backoff/jitter.

**Zdalne notatki i cache:** `<login>/Notes` musi zawierać zwykłe Markdown `.md` (opcjonalny elastyczny YAML front matter), możliwe do edycji wprost na GitHubie. Aplikacja zachowuje nieznane pola/metadane i wykrywa zdalne edycje. **Potwierdzone notatki nie są stale przechowywane w Outboxie.** Można je trzymać w RAM lub opcjonalnym, usuwalnym cache SQLite per konto; cache zawsze da się odbudować przez GitHub API i nie może zawierać jedynej kopii niewysłanej zmiany. Jeśli cache jest pusty i urządzenie jest offline, obiecuj tylko widoczność notatek z Outboxa, nie całego repo Notes. Konflikt wyświetla porównanie i chroni obie wersje; zero niewyjaśnionego `last-write-wins`.

**Bez automatycznych migracji:** nowe wersje publicznego SQLite buduje GitHub Actions po ręcznej edycji generatora i testów golden ZIP; aplikacja sprawdza manifest, kompatybilność, SHA-256 i atomowo aktywuje nowy snapshot. Nie migruje publicznego SQL na urządzeniu. W `IndexedDB` unikaj sztywnej schemy dla payloadów: rekordy elastyczne JSON. Niewielka schema techniczna IDB (object stores / indeksy) również ma być stabilna; jeżeli kiedyś konieczna jej zmiana, wymaga jawnego planu zachowania istniejącej kolejki i dowodu bezstratnego upgrade — **nie czyść IDB dla wygody**.

**Test nieblokowania funkcji przez locale:** `uiLocale=en` + grecki TR z polskimi glosami, `uiLocale=pl` + TR z angielskimi glosami, wyboru polskich przekładów przy EN UI i angielskich przy PL UI; zmiana języka ekranu nie kasuje wyboru warstw, URL ani szkicu. Screenshoty obu konfiguracji.

**Testy przed akceptacją architektury:** obowiązkowy mały eksperyment w późniejszym PR, nie w tym planistycznym, na prawdziwym Pixelu/Phosh/Alpine/Flatpak oraz Linux Mint x64, X13s Ubuntu ARM64, Windows WebView2, Android WebView, iOS WKWebView: `indexedDB.open`, transakcyjny `put`, fizyczny restart aplikacji, odczyt niepotwierdzonego payloadu, podmiana publicznego SQLite, upgrade builda/sandboxa, zapis z 2 okien/procesów, ponowne logowanie i opróżnienie outboxa dopiero po potwierdzeniu przez stub GitHub. W WWW Chrome/Firefox/Safari: trzy karty i transakcje/lease. Mierz i opublikuj w PR status PASS/FAIL na każdej platformie; nie uznawaj web engine za równoważny fizycznemu urządzeniu. Jeżeli IndexedDB zawiedzie na dowolnym wymaganym targetcie, **nie implementuj po cichu dodatkowego JSON lub adaptera**, lecz przedstaw dowód, wpływ i najprostszą możliwą alternatywę do decyzji właściciela. Obecny benchmark SQLite/OPFS nie zastępuje tego dowodu.

### 5.2. Wielojęzyczny UI, treści i adnotacje — PL i EN od początku, łatwa rozbudowa

**To twarde wymaganie, nie praca „na kiedyś”:** od pierwszego wydania po migracji **każda funkcja UI musi mieć kompletne lokalizacje `pl` i `en`**: menu, nawigacja, nagłówki, przyciski, stany pustki, błędy, walidacje, progres aktualizacji, logowanie, synchronizacja, dialogi, komunikaty offline, help/tooltipy gramatyczne, dostępność (`aria-label`, `title`, opisy screen readera), daty i liczby. Kod źródłowy JS pozostaje bez TypeScriptu. Pliki `pl.json`, `en.json` lub małe JS object maps w `app/src/i18n/` są utrzymywane przy zmianach funkcji. Nie dodawaj ciężkiego frameworka i18n, jeśli zwykłe `t(key, params)` + `Intl.*` wystarcza; użyj standardu ICU plural tylko tam, gdzie ma to uzasadnienie. Test CI blokuje brak klucza, nieprzetłumaczony placeholder, brak podstawowej lokalizacji albo rozjazd liczby zmiennych w PL/EN.

**Niezależne osie wyboru — NIE ograniczaj treści językiem aplikacji:**

1. `uiLocale`: wyłącznie język interfejsu, początkowo `pl` lub `en`; wykryj system/przeglądarkę przy pierwszym uruchomieniu, ustaw bezpieczny fallback i daj widoczny przełącznik języka. Zmiana bez restartu i bez zmiany aktualnej strony/scrolla; mały zapis preferencji w **tym samym** IndexedDB `preferences` (dla read-only WWW rozważ parametry URL/deep link pod SEO). Nie używaj locale UI jako filtrującej listy tekstów.
2. `textSources`/`contentLocales`: osobny wybór dostępnych przekładów i tekstów — TNP, UBG, KJV, TR i pisma ojców niezależnie od PL/EN UI. Angielski UI ma nadal oferować polskie przekłady, a polski UI — angielskie; wyświetlaj jasne nazwy i język źródła, nie wyłączaj funkcji.
3. `annotationLayers`: osobny zestaw niezależnych, możliwych do wielokrotnego wyboru warstw: polski gloss nad greką, angielski gloss, gramatyka, wymowa, Strong, lemma i przyszłe niemieckie/inni języki. **UI po angielsku + polskie glosy nad TR MUSI działać**, podobnie polski UI + angielskie glosy; w przyszłości polski UI + niemieckie glosy. Dostępność danej warstwy zależy od **posiadanych i licencjonowanych danych**, nie od języka przycisków. Jawnie informuj o brakach bez imitowania tłumaczeń.

**Minimalistyczny UX wielojęzyczności:** główny czytnik i pasek nawigacji pokazują tylko elementy potrzebne do czytania. Oddziel „Język interfejsu” od „Przekłady Biblii” oraz od „Warstwy nad greką”. W panelu **„Warstwy i języki” / „Layers & languages”** domyślnie pokaż kilka najczęstszych, świadomie dobranych opcji; pełny wybór dostępny po „Więcej…” / „More…”. Dla danej warstwy i języka użytkownik może włączyć konkretny język spośród faktycznie dostępnych; ustawienia pamiętane per użytkownik/urządzenie i możliwie per rodzaj czytnika. Nie twórz wielkiego stale widocznego katalogu wszystkich przyszłych języków, nie dodawaj po jednym globalnym przełączniku dla każdego nowego języka, nie dodawaj wymuszonego automatycznego tłumaczenia treści. Możliwy osobny „profile”/preset i rozsądne domyślne preferencje; użytkownik może dowolnie zmienić.

**Brak zamiany tłumaczeń Biblii na tłumaczenia UI:** nie tłumacz automatycznie wersetów ani tekstów źródłowych, nie modyfikuj tekstu TR i nie mieszaj lokalizacji z danymi Strong. Lokalne tłumaczenie *metadanych UI* nie zmienia tekstu naukowego. Zachowaj oznaczenia języka `lang` dla fragmentów polskich, angielskich i greckich (`grc`) oraz dostępność czytnika/screen readera. Normalizacja wyszukiwania, odmiany gramatyczne i wyrównanie greka–polski/angielski wymagają testów osobno od ustawień UI.

**SEO i locale:** zaprojektuj stabilny układ adresów `/<locale>/...` dla PL/EN lub równoważną prostą konwencję, z `hreflang`, `lang` w HTML, osobnymi meta title/description i nawigacją językową. Nie generuj niepotrzebnych kopii *identycznych* treści biblijnych: wyjaśnij wybór kanonicznych wersetów, ryzyko 2× liczby statycznych HTML oraz budżet Pages, sitemap i testy `canonical`/`hreflang` dla obu języków. Bez JS HTML ma zawierać realny tekst; nie używaj tylko `robots` lub automatycznej translacji tekstu źródłowego. Zmiana języka UI nie może zgubić głębokiego linku do aktualnej referencji.

**Flathub, Google Play, Apple App Store — PL/EN METADANE NA BIEŻĄCO:** źródła *wszystkich lokalizowalnych, wspieranych przez dany sklep* tekstów w **dwóch językach** muszą leżeć w repo i być zmieniane razem z funkcją/release: nazwa/opis krótki/długi, keywords, release notes, help, privacy/disclosure, opisy screenshotów, podpisy promocyjne, a także sklepowe screenshoty w PL i EN tam, gdzie platforma tego wymaga. Flathub używa metadanych AppStream/metainfo z tłumaczeniami `xml:lang` na `name`, `summary`, `description`, `keywords`, `captions` itd.; angielski wpis domyślny bez `xml:lang`. Google Play ma lokalizowane Store Listings i grafiki; App Store Connect lokalizowane metadane oraz screenshoty. Nie „tłumacz na bieżąco” przez runtime API/LLM: chodzi o **utrzymywanie i review obu katalogów w każdym PR**; repo musi zawierać gotowe pliki i automatyczną walidację CI. Nierozliczone tłumaczenia są blockerem PR, a nie zadaniem po release.

**Testing i Definition of Done dla każdej zmiany UI/feature:** CodeceptJS `Feature` / `Scenario('I ...')` lub czytelne `I.*` po DSL w JS, na **PL i EN** w próbkach każdego rodzaju widoku: menu, rozdział, werset, porównanie, słownik, interlinear, tagi, login/notatki i zgody, brak sieci, update i pobieranie z zakładki Aplikacja. Zaplanuj screenshoty desktop/mobile w obu językach, widok panelu języków oraz przypadek `UI=en; annotation=pl` i `UI=pl; annotation=en/de` (DE dopiero gdy są dane), screenshoty przed/po w PR, baseline visual diff na obu językach, brak obciętych/wylewających się napisów, działanie Unicode/greki, `lang`, screen reader i klawiaturę. Na każde nowe pole/feature dochodzi PL+EN tłumaczenie i test parytetu. Testy metadata CI sprawdzają kompletność kluczy, format Flathub XML, locale kodowane w manifestach i wskazanych platformowych listingach. **Nie wstrzymuj całej dostawy z powodu braku niemieckich glos — to osobna warstwa danych; UI musi być gotowy do rozbudowy.**

## 6. Bezwzględne wymaganie: wiele kart WWW, kilka okien/instancji

To **kryterium akceptacji**, a nie przyszła opcjonalna optymalizacja.

**Z punktu widzenia użytkownika:** Mogę mieć trzy karty WWW (np. J 1:1, 1Kor 11 i słownik), skakać między nimi, zostawiać je na później, przewijać i korzystać z nawigacji, a żadna nie resetuje innej. Każda karta zachowuje własny URL, własny werset, zaznaczenie, filtr, scroll, modal i back/forward. Nie wymagam równoczesnego odczytu z dysku co do milisekundy — **odczyty mogą być kolejkowane**, ale kolejka nie może kończyć się deadlockiem lub niezrozumiałym błędem. Długotrwałe renderowanie/edytowanie w jednej karcie nie może zablokować pozostałych.

**Browser `opfs-sahpool`:**

- Wykorzystaj sprawdzony już POC z **Web Locks API** na wspólnej nazwie blokady *per origin + wersja indeksu*, krótkim zakresem krytycznym i sygnalizacją „oczekuję na dane” dopiero przy rzeczywistym opóźnieniu. Nigdy nie trzymaj blokady podczas interakcji UI.
- Pod wyłączną blokadą: inicjalizacja i import, otwarcie SQLite, odczyt/przygotowanie danych, zamknięcie SQLite oraz **`pauseVfs()`**. Przy kolejnej operacji `unpauseVfs()` / ponowne otwarcie pod tą samą blokadą. Nie zakładaj, że samo `db.close()` zwalnia uchwyty SAH. Jeżeli technicznie uda się zapewnić bezpieczny współdzielony worker/owner, oceń go, ale nie wprowadzaj dodatkowego procesu bez jasnej poprawy prostoty.
- Zadbaj o współbieżny reset i aktualizację migawki, utratę/awarię karty, powrót z uśpienia i przestarzałe workery, brak Web Locks, `NotFoundError` przy zimnym starcie, brak niekończącej się kolejki. Rozróżnij czytelnika starej wersji i import nowej.
- Użyj `BroadcastChannel` **wyłącznie** do powiadomień o aktualizacji / unieważnieniu cache i ewentualnie koordynacji stanu; NIE traktuj go jako niezawodnego mutexu. Nie synchronizuj automatycznie bieżącego wersetu pomiędzy kartami, bo to złamałoby niezależność.
- **Wiele kart WWW:** w zatwierdzonym read-only nie otwierają prywatnych notatek; niezależne karty współdzielą publiczną SQLite przez Web Locks/SAH Pool. W ewentualnym WWW writable karty współdzielą JEDEN transakcyjny IndexedDB Outbox, a pojedynczego synchronizatora wybiera krótki Web Lock / lease; nie blokuj na czas sieci transakcji IDB. **Wiele okien/instancji Tauri:** korzystają z TEGO SAMEGO IndexedDB Outbox JS i koordynacji lease/transaction; wymagaj testu wspólnego profilu danych/`origin` i zachowania po aktualizacji. Nie zakładaj automatycznie, że osobne WebView dzielą IndexedDB.

**Tauri:** dwie lub więcej okien/instancji (różne procesy) muszą móc równocześnie czytać ten sam *read-only* snapshot SQLite. Otwieraj go w trybie tylko do odczytu; przed podmianą zamknij uchwyty, przetestuj równoległe zapytania oraz bezpieczną aktywację nowej kompletnej bazy. Zaplanuj nazwy plików z hashem, atomową zmianę wskaźnika aktywnej wersji, zachowanie starej wersji do czasu zamknięcia czytelników i bezpieczne sprzątanie. **Zapisy niewysłane dotyczą wyłącznie rekordów `pending_changes` w wspólnym IndexedDB per konto**; potwierdzone zdalne notatki są tylko w pamięci lub usuwalnym cache, a spójność zapisu zabezpieczają transakcje i lease z fencing tokenem. Odróżnij wiele okien na jednym urządzeniu od synchronizacji **między urządzeniami** przez GitHub.

Przewidź **CodeceptJS acceptance scenarios**: trzy karty z trzema różnymi wersetami, równoległe wyszukiwanie, import i odczyt w innej karcie, 5× przełączanie, zamknięcie karty z aktywnym importem, crash workera, offline/online, restart aplikacji, aktualizacja manifestu podczas czytania, wiele instancji Tauri, równoczesna edycja tych samych prywatnych notatek. Screenshoty w stałych punktach, test braku błędów w konsoli, limity czasu i brak flakiness.

## 7. GitHub: automatyczne logowanie, jedno prywatne repo `Notes`, uprawnienia do wspólnego repo — BEZ PAT i BEZ SERWERA

**Wymaganie obowiązkowe dla natywnej aplikacji Tauri.** Użytkownik widzi „Zaloguj przez GitHub”, własne „Notatki” i — tylko gdy ma aktualne uprawnienia — edycję wspólnych danych. Nie generuje PAT, nie zakłada ręcznie repo, nie instaluje Git i nie konfiguruje synchronizacji. Autoryzację i ewentualną instalację GitHub App potwierdza w GitHubie, prowadzi go przez to aplikacja. **Dla WWW bez możliwego bezserwerowego auth obowiązującym wariantem jest odczyt publicznych danych bez logowania**. Nie projektuj fałszywego loginu ani niezabezpieczonych zapisów w Pages.

### 7.1. Trzy role — nie myl tożsamości z prawami zapisu

1. **Czytelnik anonimowy:** czyta publiczne dane bez GitHub. W WWW read-only nie ma edycji ani zdalnych notatek (tylko stan nawigacji niezależny per karta; trwałe preferencje, jeśli są, nie mogą być mylone z kolejką niewysłanych zmian ani z kanonicznymi notatkami). W Tauri może tworzyć niewysłane szkice przed logowaniem w osobnym lokalnym anonimowym Outboxie; późniejsze przypisanie do konta wymaga świadomej akceptacji, aby nie wyciekły przy przełączaniu kont.
2. **Każdy zalogowany użytkownik GitHub (Tauri, ewentualnie WWW po udowodnieniu bezserwerowego auth):** niezależnie od praw do publicznego repo może czytać i edytować **swoje** notatki. Docelowy przepływ automatycznie znajduje lub tworzy jego prywatne repozytorium **dokładnie `Notes`**, po czym wznawia synchronizację. Sam fakt zalogowania **nie** daje edycji wspólnych tagów.
3. **Zalogowany współautor:** ma wszystkie prawa czytelnika + możliwość zapisu **tylko do wspólnego** `tometchy/KazdyDzienZJezusem`, jeżeli użytkownik posiada aktualne uprawnienie GitHub `write`/`maintain`/`admin` (lub odpowiednią rolę niestandardową), GitHub App ma właściwy dostęp do repo i `Contents:write`, a reguły gałęzi pozwalają na żądaną operację. W przypadku branch protection planuj branch + PR, nie omijanie ochrony.

### 7.2. Dokładnie jedno prywatne repozytorium `Notes` na konto GitHub

**Warunek bezwzględny: dokładna nazwa `Notes` (duże N), właściciel = zalogowany użytkownik, `private: true`, jedno repo na konto, bez alternatywnych nazw.** Nie `KazdyDzienZJezusem-Notes`, nie `Notes-2`, nie konto organizacji i nie jedno repo na urządzenie. Jest to logiczny zdalny magazyn notatek tego użytkownika, a nie jego lokalna kopia SQLite.

**Wymagany przebieg doświadczenia:**

1. Otwieram **aplikację Tauri**, wybieram „Zaloguj przez GitHub”. Aplikacja przeprowadza mnie przez autoryzację w GitHubie (rekomendowany natywny GitHub App Device Flow) i wraca do poprzedniego fragmentu bez utraty lokalnych szkiców. Nie tworzę PAT. **W WWW** ten krok istnieje tylko jeśli Codex udowodni bezpieczny, wspierany wariant **bez serwera**; w przeciwnym razie WWW jest read-only, bez loginu.
2. Aplikacja potwierdza tożsamość przez uwierzytelnione GitHub API (`GET /user`, używaj stabilnego identyfikatora numerycznego do izolacji danych), wyjaśnia podczas autoryzacji tworzenie prywatnego magazynu i uzyskuje wymagane uprawnienia. Przy GitHub App uwzględnij instalację na koncie osobistym, dostęp do repo i ograniczenia user access token.
3. Sprawdza repo **`<login>/Notes`**. Jeśli prywatne repo należy do tego użytkownika i jest dostępne, podłącza je **bez tworzenia następnego**. Jeśli repo nie istnieje, wywołuje udokumentowane `POST /user/repos` z `name: "Notes"`, `private: true` i minimalnymi uprawnieniami. Następnie sprawdza `private`, właściciela, token i dostęp instalacji. Automatycznie inicjalizuje wyłącznie własny obszar notatek, nie nadpisując istniejących plików. Zmiana właściciela/rename repo przez GitHub wymaga rozpoznania i bezpiecznej rekonfiguracji, nie utworzenia kopii bez zastanowienia.
4. Jeśli **`Notes` już istnieje**, ale zawiera inne pliki: **nie kasuje ich ani nie przejmuje bez walidacji**, pracuje tylko we własnej przestrzeni np. `kdzj/notes/` po potwierdzeniu zgodności albo wyświetla prosty komunikat wymagający zgody. Jeśli `Notes` jest publiczne, należy do niewłaściwego konta, nie ma praw lub jest niedostępne: **nigdy nie zapisuj prywatnych danych publicznie, nie twórz innej nazwy**, pokaż problem i zachowaj lokalne notatki w kolejce; ewentualne ustawienie prywatności wymaga jawnej zgody i sprawdzenia, czy jest wykonalne.
5. Jeśli dwie karty lub dwa urządzenia rozpoczynają logowanie i tworzenie `Notes` jednocześnie, operacja jest **idempotentna**: jedno tworzy, drugie po błędzie konfliktu/istnienia ponownie odczytuje i weryfikuje to samo repo. Żadnego automatycznego tworzenia `Notes-1` itp. Po utworzeniu repo przez użytkownika sprawdź, czy GitHub App uzyskała dostęp do nowego repo (instalacja `all repositories` vs `selected repositories`; sprawdź oficjalną semantykę repo utworzonych przez App), a gdy wymaga to zatwierdzenia na GitHubie, poprowadź użytkownika i zachowaj kolejkę lokalną.
6. W interfejsie pojawia się stan **„Notatki: zapisane lokalnie / oczekują na internet / synchronizacja / zsynchronizowane / wymagają uwagi”** i automatyczna synchronizacja. Po ponownym uruchomieniu nie trzeba konfigurować repo jeszcze raz. Jeśli token wygasł, potrzebne jest ponowne zalogowanie, lecz notatki pozostają na urządzeniu.

**Przygotuj specyfikację wszystkich odpowiedzi i błędów API**, w szczególności nieistniejące repo, brak uprawnienia `Repository creation:write` albo `Administration:write`, niezainstalowana App, `401/403/404/409/422`, utrata łączności, wygaśnięcie tokenu, repo już istniejące, repo publiczne, usunięte lub zmienione. `404` może oznaczać brak dostępu, więc nie zawsze wolno zinterpretować je jako „repo nie istnieje”. Uwzględnij, że niektórzy użytkownicy nie mogą tworzyć repo z powodu polityk konta/organizacji: notatki nie mogą przez to zniknąć.

### 7.3. Local-first: notatka najpierw na urządzeniu, potem na GitHub

- Każda nowa/zmieniona notatka jest **trwale zapisywana lokalnie PRZED komunikatem „Zapisano”**. Po zapisie lokalnym UI natychmiast pokazuje treść, niezależnie od Internetu, tokenu i dostępności GitHub. Nie jest dopuszczalna sama kolejka w pamięci procesu, `setTimeout` ani pozostawienie niesynchronizowanego tekstu jedynie w DOM.
- **WWW:** domyślnie read-only pod SEO; ewentualny writable-web wymagający bezserwerowego auth użyje **tego samego IndexedDB Outbox** co Tauri. **Tauri:** IndexedDB WebView z `pending_changes` per `accountId`, zawierające **TYLKO niewysłane operacje i konflikty**, całkowicie poza wymienialną publiczną SQLite. Po publikacji wpis/payload jest usuwany, a odczyt zdalnych notatek następuje przez API / usuwalny cache. Elastyczny JSON w rekordach IndexedDB nie wymaga zmian schematu publicznego SQL.
- Model kolejki w jednym formacie JSON (rekord IndexedDB dla Tauri i ewentualnego WWW writable) zapisuje **cały tekst niewysłanej notatki i operację razem**, identyfikator UUID/idempotencyjny, podstawę zdalnej wersji SHA/ETag, numeryczne ID konta GitHub, licznik prób i stan błędu. **Prywatne repo `Notes` musi zawierać wyłącznie zwykłe, czytelne dla człowieka pliki Markdown `.md` dla notatek**, np. `kdzj/notes/<stable-id>.md` (inne pliki użytkownika w repo nie są przez aplikację ruszane). Zdefiniuj elastyczny format Markdown: UTF-8, naturalny Markdown jako treść, opcjonalny YAML front matter z referencjami biblijnymi/ID/datami, zachowywanie nieznanych pól i formatowania przy edycji. Nie narzucaj sztywnego schematu wymagającego migrowania wszystkich istniejących notatek. Notatki mają dać się swobodnie tworzyć i edytować **bezpośrednio w interfejsie GitHub**, a następne `sync/pull` w aplikacji wykrywa takie zmiany i odświeża *usuwalny* cache lub pamięć bez kasowania lokalnych niezapisanych edycji; zatwierdzone notatki nie pozostają w trwałym Outboxie. Nie wprowadzaj zdalnego `notes.db`, JSON zamiast Markdown ani binarnego formatu notatek. Nie publikuj notatek w Pages, Actions artifacts, logach, analytics, screenshotach ani repo aplikacji.
- Przeglądarka/aplikacja może zostać **zamknięta natychmiast po zapisaniu notatki**. Po następnym otwarciu odczytuje lokalną notatkę i outbox, ustala stan autoryzacji, a po odzyskaniu sieci wysyła oczekujące operacje. Nie obiecuj background sync podczas zamkniętego procesu: gdy aplikacja jest zamknięta, nic nie musi działać, ale **żadna operacja nie może zginąć**. Zaplanuj wznowienie na `online`/focus/start, retry z backoff i jitterem, błędy rate limit i status synchronizacji.
- Dwie karty WWW zawsze mogą niezależnie czytać publiczne treści przez Web Locks/SAH Pool; **read-only WWW nie ma synchronizatora Notes**. Przyszłe writable WWW i Tauri korzystają ze **wspólnego IndexedDB Outbox + Web Locks/lease per konto** dla synchronizatora, z transakcjami, generation/fencing i dowodem współdzielenia przez WebView. Oddzielnie rozwiązuj współbieżność różnych urządzeń, które nie współdzielą lokalnej bazy IndexedDB. Nigdy nie zmieniaj aktualnie otwartego wersetu, scrolla ani historii drugiego okna.
- GitHub API: optimistic concurrency z SHA/ETag/commit, `409/422` i zmianami równoległymi; odczyt i aktualizacja zdalnej wersji przed zapisem, bez niejawnego `last-write-wins`. Rozstrzygaj przypadki: dwa urządzenia zapisują ten sam UUID offline, konflikt edycji/usunięcia, częściowo udany upload, błąd odpowiedzi po skutecznym commicie, reinstall i ponowny import, przełączanie kont. Zdefiniuj scenariusz jawnej decyzji użytkownika przy konflikcie (zachowaj obie wersje i możliwość porównania).
- Zabezpiecz dane przy wylogowaniu i przełączaniu kont: nie wymieszaj notatek różnych kont, nie wyświetlaj poprzedniemu użytkownikowi cudzych treści, nie usuwaj niezsynchronizowanych notatek bez wyraźnego potwierdzenia i możliwości eksportu. Uczciwie opisz prywatność plików lokalnych na współdzielonym urządzeniu; przeanalizuj szyfrowanie/hasło odblokowujące, ale nie udawaj, że GitHub private chroni lokalne dane.

### 7.4. Dynamiczne prawo do zmiany wspólnej Biblii, tagów i innych publicznych danych

**Test obowiązkowy dla Markdown:** utwórz notatkę w aplikacji, zsynchronizuj `.md` do prywatnego `Notes`, edytuj ten sam plik ręcznie w edytorze GitHuba, ponownie uruchom synchronizację i zobacz zdalną zmianę w aplikacji; następnie powtórz z równoległą lokalną edycją offline i sprawdź zachowanie obu wersji, brak strat, brak `last-write-wins`.

**Nie prowadź własnej listy użytkowników. Dotyczy zapisu w Tauri oraz w WWW tylko w razie udowodnionego bezserwerowego auth; WWW read-only nie pokazuje przycisków edycji.** Właściciel dodaje/odbiera dostęp do zapisu w **`tometchy/KazdyDzienZJezusem`** zwykłymi ustawieniami Collaborators/Teams GitHub. Aplikacja ma automatycznie uwzględnić tę zmianę na kolejnym odświeżeniu, zalogowaniu, wejściu na ekran edycji, powrocie do aktywnej karty lub po krótkim, udokumentowanym czasie ważności cache.

- Po logowaniu i przy `focus`/manualnym „Odśwież uprawnienia” sprawdzaj przez GitHub API tożsamość oraz skuteczne prawa do repo: użytkownik (role `write`, `maintain`, `admin` / custom role), uprawnienia **user token**, instalację GitHub App i `Contents:write`, reguły gałęzi/PR. Rozróżnij brak dostępu od braku sieci lub rate limit; nie utrwalaj prawa `write` bez terminu ważności. Nawet jeśli UI ostatnio pokazywał edycję, **każdą próbę remote write wykonuj wyłącznie autoryzowanym tokenem użytkownika, zweryfikuj uprawnienia przed wysyłką i honoruj odmowę GitHub**. UI nigdy nie jest zabezpieczeniem.
- Użytkownik z nowo przyznanym dostępem: po odświeżeniu ma widzieć akcje edytowania wspólnych `tags/*.md` i innych świadomie dopuszczonych ścieżek. Użytkownik, któremu odebrano uprawnienie: po odświeżeniu **nie widzi już aktywnego zapisu**; API nie może wykonać zmiany nawet ze starej karty. Stary lokalny projekt zmiany może zostać jako prywatny szkic, ale **nie** jako kolejka zapisów współdzielonych wykonywana w tle po utracie uprawnień.
- Jeśli zapis do `master` jest zablokowany zasadami gałęzi, aplikacja tworzy branch i PR **tylko jeśli użytkownik ma prawo do tych operacji**. Zmiana skutecznie opublikowana na GitHubie powinna trafić do nowej wersji wspólnej migawki przez Actions; przeglądarka i Tauri wykryją aktualizację bez tracenia lokalnych notatek/stanów kart. Opisz czy/na jakiej podstawie możliwy jest preview jeszcze nieopublikowanych tagów.
- Uprawnienia do wspólnego repo **nie są uprawnieniami do `Notes` innego użytkownika**. Nigdy nie używaj shared app installation tokenu o prawach do wspólnego repo do zapisywania zmian w imieniu dowolnego czytelnika. Nie edytuj przypadkowych plików publicznego repo — dopuść tylko świadomie określone ścieżki, walidację nazw i ograniczenia rozmiaru.
- Sprawdź szczegóły `GET /repos/{owner}/{repo}/collaborators/{username}/permission` i repo metadata permissions, możliwości tokenów GitHub App oraz branch protection. Gdy endpoint wymaga dodatkowych praw, zaproponuj bezpieczną możliwość potwierdzenia **realnej** operacji użytkownika lub inną weryfikację (nie zgaduj praw na podstawie samego publicznego repo).

### 7.5. Logowanie bez PAT: absolutny zakaz własnego backendu oraz zatwierdzony fallback WWW read-only

**Decyzja właściciela — NIE pozostawiaj jej do ponownego uzgadniania:**

1. **Nie będzie żadnego własnego serwera do OAuth, nawet „minimalnego”:** ani utrzymywanego VPS, ani serverless Function, ani Cloudflare Worker, ani proxy/CORS gateway, ani usługi wymieniającej kod OAuth, ani pośrednika przechowującego tokeny. Nie obiecuj rozwiązań, które wymagają uruchomienia takiej usługi przez właściciela. GitHub Actions służy tylko do budowania/CI/publikacji; nie może być interaktywnym backendem sesji ani kolejką prywatnych notatek. GitHub jako dostawca tożsamości i API jest dozwolony — własny dodatkowy backend NIE.
2. **Tauri musi zapewnić login bez PAT.** Projektuj **GitHub App Device Flow**: użytkownik klika login, przechodzi do GitHuba i autoryzuje urządzenie, wraca do Tauri; aplikacja weryfikuje użytkownika, ma minimalne uprawnienia do Notes i opcjonalnie do wspólnych danych. Device Flow działa bez client secret, także refresh tokenu uzyskanego tym sposobem (sprawdź aktualne warunki i przydatność natywnego secret storage). Natywna warstwa HTTP może wysyłać żądania do `github.com` / `api.github.com`, gdy WebKitGTK ma ograniczenia CORS, ale **biznesowy flow, reguły uprawnień, Notes/outbox, konflikt i GitHub REST API pozostają wspólne w JS**. Warstwa Rust jest wąskim, audytowalnym transportem/secure storage, nie implementuje drugiej aplikacji.
3. **WWW na GitHub Pages:** Codex ma rzetelnie opisać, czy *bez* pośrednika, `client_secret`, tokenów statycznych, anonimowych proxy i sztuczek CORS istnieje aktualnie wspierana metoda pełnej autoryzacji użytkownika w przeglądarce. Sprawdź standardowy GitHub App/OAuth web flow, PKCE, Device Flow, CORS i token refresh. **Nie implementuj ani nie proponuj dodatkowego serwera jako rekomendacji.** Jeśli nie możesz dowieść działającego i bezpiecznego flow, zaprojektuj produkcyjną **GitHub Pages read-only z pełną wartością SEO**, bez logowania i edycji. To rozwiązanie jest **zaakceptowanym wynikiem**, nie blokerem i nie wymaga ponownej zgody właściciela. Dopuszczalna w przyszłości rozbudowa auth WWW może korzystać tylko z udowodnionego bezserwerowego flow — nie dodawaj go na siłę.
4. **Brak PAT dla końcowego użytkownika:** nie wymagaj ręcznego generowania classic/fine-grained PAT, wklejania tokenów, klonowania repo albo uruchamiania git CLI. Nie trzymać access/refresh token w `localStorage`, URL, logach, HTML czy screenshotach. Natywne sekrety w odpowiednim systemowym magazynie (albo innym udokumentowanym bezpiecznym rozwiązaniu z analizą dostępności na postmarketOS). Nigdy nie wbudowuj `client_secret`, GitHub App private key ani tokenu w publiczny JS lub binarkę.
5. **Nie myl UI z bezpieczeństwem:** GitHub API egzekwuje prawa przy każdym remote write. Token GitHub App user access ma ograniczenia wynikające z dostępu użytkownika, instalacji App i jej własnych uprawnień. Gdy użytkownik utraci dostęp do wspólnego repo, kolejny zapis musi się zakończyć odmową, a UI po odświeżeniu ma wyłączyć edycję. To nie może blokować jego prywatnych `Notes`.

**Dowody, nie deklaracje:** zbadaj oficjalną dokumentację GitHub dotyczącą `client_secret`, CORS, Device Flow, token refresh, `Repository creation:write`, `Contents:write`, GitHub App installation i zakresów tokenów. Nazwij osobno to, co jest udokumentowane, co wymaga eksperymentu na realnym urządzeniu i co jest niemożliwe/nieudowodnione w statycznym WWW. W **tym** dokumentacyjnym PR nie implementuj eksperymentów. Przygotuj plan ich wykonania w osobnym, małym PR, ale wybór produkcyjnego fallbacku read-only jest już przesądzony.

**Wymagane testy i UX dla Tauri**: pierwszy login tworzy prywatne `Notes`; dziesięć kolejnych logowań nie tworzy nowego; dwa okna/urządzenia równolegle; istniejące prywatne `Notes`; niebezpiecznie publiczne `Notes` blokuje zapis; notatka offline zachowana po zamknięciu i po następnym otwarciu wysłana automatycznie; konto odłączone/przełączone; repo usunięte; cofnięcie i przyznanie `write` do repo publicznego. **W WWW read-only testuj brak interfejsu logowania/edycji, brak tokenów i utrzymanie pełnego publicznego czytnika/SEO.**

### 7.6. Migracja ze zwykłego Git CLI w kontenerze na GitHub REST API w JavaScript

**Zbadaj obecny kod**, przede wszystkim `KazdyDzienZJezusem/Services/TagGitStore.cs`, `TagEditingService.cs`, `GitHubWriteAccess.cs`, `TagRepository.cs`, obecne testy z lokalnymi bare Git remotes, `scripts/git-sync.sh`, `compose.yaml` i `README.md`. Obecnie proces w kontenerze używa dedykowanego klona, `git fetch`, `reset --hard`, `add`, `commit`, `push`, retry przy konfliktach, sesji w Redis oraz dodatkowego read tokenu. **Nie przenoś tego klona i tych mechanizmów do aplikacji użytkownika.** Odróżnij stary runtime od procesów developerskich i buildów w GitHub Actions.

**Warunek architektoniczny: finalny runtime (Tauri i WWW) nie wymaga zainstalowanego `git`, repo checkout, SSH, GIT config, serwerowego read tokenu, ani uruchamiania komend git w child process.** Wszystkie zdalne operacje wykonuje **jeden wspólny moduł JavaScript klienta GitHub REST API** z wyraźnymi operacjami domenowymi. Gdy Tauri z powodów CORS korzysta z Rust/HTTP, jest to jedynie adapter transportowy; aplikacja nie może duplikować całej logiki GitHub w Rust. Gdy WWW jest read-only, nie żąda tokenu GitHub; publiczne dane otrzymuje z opublikowanej, wygenerowanej na CI migawki i statycznych HTML. W CI `actions/checkout`, Git CLI oraz skrypty generatorów mogą nadal służyć do publikacji i kontroli historii — to nie runtime.

**Obowiązkowa tabela stare Git → nowy REST w dokumentacji:**

| Obecne działanie serwera | Docelowa operacja w JS + GitHub REST API |
| --- | --- |
| `git clone`, `fetch`, `reset`, odczyt checkoutu | `GET /repos/{owner}/{repo}` i odczyt konkretnych plików / commitów / drzew: `GET /repos/{owner}/{repo}/contents/{path}` lub Git Trees API; brak lokalnego klona |
| `git add` + `commit` + `push` pojedynczego taga albo pliku Notes | `PUT /repos/{owner}/{repo}/contents/{path}`: Base64 treści, `message`, `branch`, aktualne `sha` przy update; sprawdzony `owner`, `repo`, dozwolona ścieżka |
| Wiele plików w jednej zmianie | Git Data REST: blobs → tree z poprawnym `base_tree` → commit z aktualnym parent SHA → aktualizacja ref z ochroną przed wyścigiem; bez force-push |
| Branch/PR, gdy `master` chroniony | odpowiednie REST refs/branches/pulls; uwzględnij prawa tokenu i branch rules |
| Weryfikacja uprawnień / sesji | `GET /user`, sprawdzenie bieżących uprawnień do repo i efektywnego prawa zapisu, dopiero autoryzowana próba remote write |
| Odpytanie o już zapisany commit / niepewna odpowiedź | `GET` zawartości/commits/ref i semantyczne sprawdzenie efektu, bez bezmyślnego drugiego zapisu |

**Specyfikuj konkretne kontrakty JS** (propozycje, bez implementacji): `github.getUser()`, `github.getRepository(owner,repo)`, `github.ensurePrivateNotesRepo(user)`, `github.readFile(repo,path,ref)`, `github.putFile(repo,path,content,baseSha)`, `github.commitBatch(repo,changes,baseCommit)`, `github.getEffectivePermissions(repo)`, `github.createChangePullRequest(...)`, `notes.syncPending()`. Preferuj małe API domenowe zamiast wystawiania dowolnego endpointu HTTP do widoków; waliduj repo, ścieżki, Unicode i rozmiary treści. 

**Wymagania weryfikacji:** sprawdź aktualne uprawnienia GitHub App token i `Repository creation:write` dla `POST /user/repos`, konieczność `Contents:write` do plików, dostęp instalacji do nowo utworzonego `Notes`, GitHub rate limits/abuse limits, 401/403/404/409/422/429, `ETag`/SHA/parent commit oraz odpowiedzi częściowo udane. `404` może oznaczać brak uprawnień. Nie interpretuj `409` jako sukcesu. Odróżnij atomiczny PUT jednego pliku od multi-file commitu; nie wykonuj dwóch konkurencyjnych Contents API writes na tej samej gałęzi. Po konflikcie pobierz nową wersję, zrób semantyczny merge lub zachowaj oba warianty i pokaż konflikt użytkownikowi — **zero cichego last-write-wins**. Rate-limit obsłuż przez backoff i respektowanie odpowiednich nagłówków. Nie wpisuj tokena do URL, request logów ani artefaktów.

**GitHub Actions jako jedyny publikator WWW:** publiczne tagi w `tags/*.md` zmienione przez autoryzowanego użytkownika przez API prowadzą do nowego commitu/PR, a potem do przebudowy statycznych HTML oraz wspólnej SQLite w Actions. Czytelnik WWW i Tauri mogą wykryć nowy manifest i wczytać wersję; nie ma serwera www reagującego na request w runtime. Planuj limity i kolejkę commitów przy częstych edycjach; nie buduj publicznych tagów przez JS bezpośrednio na produkcyjnej stronie z tokenem admina.

**Testy CodeceptJS/stubs:** odpowiedzi REST na istniejące/nieistniejące `Notes`, publiczne `Notes` (niebezpieczne), `422` przy równoczesnym tworzeniu, konflikt SHA przy zapisie, odmowa po cofnięciu `write`, branch protection i PR, 403/429/rate limit, przerwana odpowiedź po skutecznym zapisie, zmiana konta i synchronizacja outbox w wielu instancjach. Zdefiniuj testy kontraktowe HTTP i osobne, rzadsze testy sandbox GitHub API na kontrolowanym koncie, bez produkcyjnych notatek i bez sekretów w PR z forków.

**Zakaz:** nie proponuj zastąpienia Git CLI przez git-over-HTTP, isomorphic-git, klonowanie repo w przeglądarce, automatyczny push z embedded tokenem, ani odpalanie skryptu Git na urządzeniu. Tu celem jest prosty, bezpośredni GitHub REST API z uprawnieniami konkretnego użytkownika.

### 7.7. Zmiana nazwy lub właściciela głównego publicznego repo — jeden centralny parametr, bez grep/replace

Właściciel przewiduje przemianowanie `tometchy/KazdyDzienZJezusem`, a być może także przeniesienie repo. **Nie wbudowuj tej pary owner/repo w widokach, REST wywołaniach, testach, generatorach, dokumentowanych linkach pobierania ani w kluczach lokalnej SQLite.** Każdy runtime odnajduje konfigurację przez **jedno źródło prawdy** i jeden moduł `config.js` (wspólny kontrakt JS); GitHub Actions generuje ją deterministycznie.

Zaproponuj nazwy i dokładną semantykę konfiguracji, np.:

```text
KDZJ_PUBLIC_REPOSITORY=<owner>/<repo>    # publiczne repozytorium aplikacji i wspólnych tagów
KDZJ_NOTES_REPOSITORY_NAME=Notes         # STAŁA produktu, nie nazwa głównego repo
KDZJ_PUBLIC_SITE_ORIGIN=https://...     # najlepiej własna, niezmienna domena
KDZJ_UPDATE_MANIFEST_URL=https://...    # stabilny, wersjonowany URL HTTPS
KDZJ_CONTENT_MANIFEST_URL=https://...   # manifest migawek treści
```

**Uwaga:** podane zmienne są przykładami do planu, nie gotowymi sekretami ani wymogiem pięciu ręcznie wpisywanych wartości. Preferuj `github.repository` z kontekstu GitHub Actions jako *wartość domyślną* dla repo publicznego oraz **jedną opcjonalną repository variable** do nadpisania, bez edycji kodu. Emituj wygenerowany `app-config.json` na Pages i do artefaktów Tauri. JS ma używać jedynie `loadConfig()` i walidować `owner/repo`, hosty, HTTPS i wymagane wersje. Podczas pracy offline Tauri używa bezpiecznej konfiguracji zapisanej razem z aplikacją/wersją; aktualizacja publicznej konfiguracji może być odczytana po połączeniu, ale **nie może podmienić uprawnień, endpointu aktualizacji ani repo do zapisu na dowolne obce konto bez kontroli pochodzenia**. Zmiana repo write w zainstalowanych wcześniej binarkach wymaga zgodnej, podpisanej aktualizacji lub ściśle zweryfikowanego migracyjnego manifestu, a nie dowolnego JSON-u z internetu.

**GitHub Pages**: oficjalnie GitHub **nie gwarantuje przekierowania adresów project Pages** po zmianie nazwy repo, mimo że sam adres repo na github.com jest przekierowywany. Dlatego użyj docelowo **własnej domeny / stałego originu** dla SEO, treści i updatera; nie polegaj na starym `github.io/old-repo/` jako trwałym canonical/update endpoint. Zaplanuj testy 404, asset base Vite, canonical, sitemap, `robots`, dopasowanie loginu i polityk do nowej lokalizacji.

**Repo Notes jest stałe:** `<zalogowany login>/Notes` nadal nazywa się dokładnie `Notes` po zmianie głównego publicznego repo. Lokalny **Outbox JSON (Tauri) lub IndexedDB key (WWW) dla konta** identyfikuj **stabilnym GitHub numeric user ID**, a nie zmienną nazwą publicznego repo czy zmiennym loginem. Upewnij się, że dla cofniętego write access żądania trafiają wyłącznie do bieżącego, poprawnego publicznego repo. Zaproponuj test migracji repo A→B z istniejącą kolejką tagów i prywatnych notatek: notatki pozostają, a nieautoryzowane operacje shared repo zatrzymują się z czytelnym wyjaśnieniem i nie są wysyłane w ciemno.

## 8. UX i statyczny WWW, w tym zakładka „Aplikacja”

**SEO i read-only bez JS — wymaganie dodatkowe:** GitHub Pages ma publikować faktyczne dokumenty HTML przygotowane przez GitHub Actions. Googlebot i zwykły czytelnik z wyłączonym JS muszą zobaczyć tytuły, treść i linki wersetów, tagów, Ojców i innych publicznych materiałów. JavaScript/Unpoly dopiero wzbogaca nawigację i wyszukiwanie o fragmentowe aktualizacje; nie wymaga się auth do czytania. Nie obiecuj w pełni indeksowalnego SEO na podstawie jedynie hash routingu. Zadbaj o sitemap, canonical, robots, `hreflang` tam gdzie uzasadniony, 404/redirect i ochronę przed podwójną indeksacją ścieżek. Link „Aplikacja” prowadzi do realnych pobrań z GitHub Releases.

Utwórz dokument z mapą nawigacji i przykładowymi **szkicami ekranów (wireframe)**, bez implementowania ich jeszcze. Zachowaj dotychczasowe funkcje i ergonomię: Biblia, przekłady, wybór księgi/rozdziału, porównanie wersetów, greka (na każdej karcie niezależnie), słowniki, przypisy, modal gramatyki, Pisma Ojców, Tagi, Szukaj, **Aplikacja**, a w **Tauri** także Notatki i Konto. **Wspólny kod może warunkowo ukrywać funkcje wymagające autoryzacji; nie buduj osobnej wersji UI.** Zachowaj mobilny układ na wąskim ekranie Phosh i czytelność na desktopie. W **Tauri** zakładka „Konto” powinna pokazywać **jedno kliknięcie GitHub**, rozpoznaną tożsamość, stan prywatnego `Notes` i bieżące prawa do wspólnych danych, z możliwością ręcznego odświeżenia uprawnień; zakładka „Notatki” pokazuje stan zapisu lokalnego i kolejki synchronizacji. W **WWW read-only** nie wyświetlaj aktywnego logowania, edycji ani prywatnych notatek — czytelnik widzi tylko publiczne funkcje i zakładkę „Aplikacja”. Login natywny ma przywracać użytkownika do tego samego fragmentu, a nie resetować na stronę główną. Linki, przyciski i przełączenia nie powinny przeładowywać całego widoku.

Strona na GitHub Pages ma zakładkę **„Aplikacja”** z listą prawdziwych, dostępnych paczek. Zasilaj ją manifestem wydania tworzonym przez GitHub Actions, a pliki pobieraj z publicznych **GitHub Releases** (trwałe i bezpośrednie linki do assetów, nie krótkotrwałe Action artifacts wymagające konta). Dla każdej pozycji: system, architektura, rodzaj pakietu, rozmiar, wersja/commit, data, SHA-256, instrukcja instalacji, czy dostępne oraz ewentualny wymóg podpisu. Nigdy nie pokazuj niedziałającego przycisku „Pobierz”. Użyj jednego spójnego manifestu i czytelnego komunikatu dla brakujących platform. Przewidź przejście do przyszłych sklepów, ale **nie uzależniaj dystrybucji od sklepów**.

**Wymagana docelowa macierz wydawania (sprawdź i rozpisz osobno build, test automatyczny, instalację, podpisanie):**

- WWW: GitHub Pages, Chrome/Chromium, Firefox, Safari/WebKit, desktop/mobile, deep-linki i multi-tab.
- Linux Mint: `x86_64` / **glibc** (np. AppImage albo .deb; sprawdź kompatybilność WebKitGTK i zależności).
- ThinkPad **X13s**: Linux **aarch64 glibc** (Ubuntu; aarch64 AppImage/deb lub uczciwie zweryfikowany pakiet).
- Pixel 3a XL: **postmarketOS / Alpine / aarch64 musl / Phosh**, osobny natywny tar.gz lub `.apk` (Alpine package), NIE Android APK. Zachowaj działający eksperyment z `WEBKIT_DISABLE_DMABUF_RENDERER=1` jako świadomą opcję tylko po potwierdzeniu potrzeby. Musi działać z ekranem dotykowym i bez internetu.
- Windows: **x86_64**, a jeśli wykonalne i opłacalne także **ARM64**; WebView2, EXE/MSI i ograniczenia podpisywania.
- Android: co najmniej **arm64-v8a** z ręcznie pobieranym, rzeczywiście instalowalnym, podpisanym APK (ew. x86_64 dla emulatora). Tauri Android jest osobnym targetem od Pixel postmarketOS. Rozpisz klucz podpisujący, sekrety Actions, aktualizacje i kontrolę integralności. Nie pokazuj niepodpisanego APK jako gotowego wydania.

Dla niespełnionych warunków pokaż „build możliwy, dystrybucja zablokowana”, zamiast wymyślonego linku. Nie wykorzystuj cudzych certyfikatów.

Sprawdź dostępność/zachowanie macOS/iOS emulatorów i Windows ARM64 oraz limity/bezpłatność **w aktualnym planie GitHub**, zamiast zakładać, że każda platforma ma taki sam runner i możliwość UI testu.

### 8.1. SEO — statyczna strona KAŻDEGO wersetu, o ile realnie mieści się w limitach Pages

To jest **nowe, jednoznaczne wymaganie do ZAPROJEKTOWANIA**; w tym PR niczego nie generuj i nie publikuj. W planie daj decyzję uzasadnioną pomiarami, a nie samą deklaracją „prerendering”. **Preferowane rozwiązanie: podczas builda w GitHub Actions wygenerować normalny HTML dla każdego istniejącego, dozwolonego do publikacji wersetu** (ok. 31 tys. unikatowych referencji dla pełnych ksiąg, lecz policz to ze źródeł obecnego checkoutu). Przykładowa kanoniczna ścieżka: `/Biblia/Werset/J/3/16/` → w artefakcie Pages `Biblia/Werset/J/3/16/index.html`. Każdy HTML zawiera wszystkie dostępne w danej referencji tłumaczenia, rzeczywisty tekst, tagi/odnośniki, link do rozdziału i sąsiednich wersetów, `title`, `description`, `lang`, `canonical`, poprawne nagłówki i dostępność. **Nie generuj 4 niemal identycznych, indeksowanych stron danego wersetu wyłącznie z powodu 4 przekładów**; przypisz kanoniczny URL i rozwiąż strony przekładów/rozdziałów tak, by unikać duplikacji SEO. Strony ksiąg, rozdziałów, tagów, Ojców, słowników oraz „Aplikacja” mają być osobnymi prawdziwymi HTML i działać bez JavaScriptu. Treści licencjonowane/atrybucje publikuj tylko w dopuszczonym zakresie; przygotuj tabelę praw do wyświetlania, indeksowania i pakowania offline.

**Nie rób osobnego systemu szablonów dla SEO i osobnego dla aplikacji.** Wytycz jedną bibliotekę **JavaScript** renderującą semantyczny widok (`renderVerse(data)`, `renderChapter(data)` itd.). Build-time generator używa tego samego renderera przy tworzeniu pełnego dokumentu z metadanymi SEO, a przeglądarka/Tauri używają go do stworzenia fragmentu HTML przekazywanego do Unpoly (`up.render`) — jedna logika widoków, brak React/Vue/Svelte/Angular/TS, brak serwera. Wariant bez JS używa zwykłych linków `<a href=...>` i statycznych stron; wariant JS zachowuje lokalnie per-karta scroll, modale, ustawienia widoku i tylko częściowo wymienia DOM. Rozdziel treść dokumentu HTML (dla botów i czytelników bez JS) od ładowanej z SQLite interaktywności.

**Budżet i decyzja go/no-go:** GitHub Pages limituje **opublikowaną stronę do 1 GB**, a **deployment do 10 minut** (zawsze odczytaj aktualną oficjalną dokumentację). GitHub Actions ma także czas na generowanie artefaktu; nie myl go z limitem wdrożenia. Każ Codexowi policzyć rzeczywistą liczbę unikatowych referencji/stron i liczbę generowanych plików oraz oszacować rozmiar HTML i czas na bazie próbki np. 1 000 rzeczywistych wersetów (pomiar wykonać dopiero w późniejszym PR implementacyjnym, nie w tym dokumentacyjnym). Uwzględnij w 1 GB również CSS, JS, WASM, dane, screenshoty tylko jeśli publikowane, i pliki sitemap; duże instalatory mają być w **GitHub Releases**, nie w Pages. Zaproponuj minimalny HTML bez powielania CSS/JS/manifestu na każdej stronie, strumieniowe/przyrostowe generowanie tylko zmienionych stron, cache builda, atomową publikację i pomiar czasu całej ścieżki z uploadem oraz deployem. Ustal margines bezpieczeństwa np. budżet wynikowy **<=800 MB** i odpowiednio niższy, zmierzony czas deployu (limit 10 min). Nie zakładaj automatycznie, że 31 000 plików zmieści się w dowolnym czasie — liczba plików ma znaczenie tak samo jak bajty.

**Fallback tylko w razie wyników potwierdzających realne przekroczenie limitu**: najpierw optymalizuj statyczne HTML, deduplikuj zasoby, zachowaj pojedyncze strony kanoniczne. Jeśli mimo tego pełny per-verse HTML okaże się niewykonalny na Pages, przygotuj dla właściciela tabelę konkretnych pomiarów i wariant minimalny (pełne statyczne rozdziały ze stabilnym fragmentem `#verse`, plus statyczne strony pojedynczych wersetów w granicach budżetu), jasno pokazując **utracony poziom SEO**. Nie przedstawiaj fallbacku jako równoważnika „każdy werset ma osobny URL i własną stronę HTML”. W tym zadaniu nie uzgadniaj zmian zakresu; plan ma wskazać kryteria i kolejność decyzji.

**Sitemap i duplikaty:** wygeneruj sitemap index + sitemapy podzielone na maksymalnie **50 000 URL lub 50 MB po rozpakowaniu na plik** (limit Google), z absolutnymi URL-ami, właściwym `lastmod` tylko gdy zawartość faktycznie się zmieniła, `robots.txt`, kanonicznymi ścieżkami i linkowaniem rozdział ↔ werset ↔ przekład/tag. Uwzględnij jedną docelową domenę (custom domain vs `github.io`) oraz nieindeksowanie duplikatów. Zweryfikuj bezpośrednie wejście z Google, refresh, 404, stare ścieżki `/Biblia/...`, bezslashowe `/Biblia/Werset/J/3/16` i ścieżki ze slashem; **Pages nie ma dowolnych reguł rewrite/redirect**, więc nie zakładaj zachowania ASP.NET Core. Zrób tabelę mapowania historycznych URL na nowy zasób z testem rzeczywistego statusu HTTP i canonical. Google nie gwarantuje zaindeksowania każdego URL tylko dlatego, że jest w sitemap.

**Test SEO:** CodeceptJS ma mieć na każdy TYP widoku co najmniej jedno `Executable Specification` uruchomione z JS włączonym oraz test ładowania bez JS (niekoniecznie screenshot każdej strony). Dla stron lokalizowanych PL/EN sprawdź `hreflang`/`canonical`, widoczny język interfejsu i brak automatycznego tłumaczenia źródłowych wersetów; mierz koszt dodatkowych URL-i oraz nie przekraczaj limitów GitHub Pages. Zrzuty ekranu na typowe rozdziały/wersety w desktop i mobile. Osobno szybki automat porównuje **zbiór wygenerowanych kanonicznych ścieżek** ze zbiorem referencji dopuszczonych do publikacji (nie tylko próbkę) i wykrywa 404/duplikat/missing page; reprezentatywną próbkę stron sprawdza pod kątem treści HTML, tytułu i canonical. To są testy SEO, a nie zastępstwo kompletnego testu danych opisanego niżej.

**Konieczne w planie:** tabela: „typ strony → liczba stron → przykładowy URL → źródło danych → rozmiar szacowany → weryfikacja bez JS → czy indeksowalne → canonical → test CodeceptJS”. Linki do oficjalnych limitów Pages/Google i mierzalny próg wykonalności.

**Wymaganie UX aktualizacji na Flathub:** w zakładce „Aplikacja” link do rzeczywistej karty Flathub (po opublikowaniu); przed publikacją dostępny pakiet testowy Flatpak z GitHub Releases tylko jeżeli jego podpis / instalacja offline są bezpiecznie opisane. Pokazuj status wersji i przycisk przekierowujący do Flathub/centrum oprogramowania, ale NIE wywołuj updatera Tauri w sandboxie Flatpak. Brak równoległego aktualizowania tych samych plików przez dwa systemy.

**Flathub to realny wariant, a nie gwarancja:** oficjalnie publikuje `x86_64` i `aarch64`, Alpine pozwala instalować Flatpaka, a Tauri 2 dokumentuje przygotowanie manifestu. **Nie wolno utożsamiać sukcesu natywnego POC Alpine/musl z sukcesem Flatpaka**. Zaplanuj proof-of-concept w kolejnym implementacyjnym PR: Flatpak na prawdziwym Pixelu/Phosh, WebKitGTK, Wayland/touch, otwieranie danych, 4 GB RAM, czas startu, renderowanie, portale systemowe, sieć, logowanie GitHub (Device Flow), trwałość prywatnego katalogu, uprawnienia sandboxa, dostęp do Downloads i test aktualizacji. Zadbaj o stabilny identyfikator `app_id` i jego zgodność przy przejściu z obecnej natywnej instalacji musl na Flatpak (osobne lokalizacje `app_data_dir` → wymagany jawny, przetestowany eksport/import lub utrzymanie tego samego profilu IndexedDB — bez strat niewysłanych rekordów; nie obiecuj automatycznej wspólnej lokalizacji między instalacją musl i Flatpakiem). Sprawdź licencje danych i wymagania Flathub, dopuszczalne uprawnienia oraz brak dostępu do sieci przy budowaniu manifestu Flathub; zbuduj i przetestuj w GitHub Actions z lintem manifestu. Opisz, jakie prace muszą być zgłoszone do osobnego repo flathub i jak aktualizacje manifestu trafią tam po wydaniu. Nie wymagaj lokalnego buildera na żadnym urządzeniu właściciela.

**Dokumentacja Tauri 2**: jego oficjalna wtyczka updater generuje/obsługuje podpisane paczki dla desktopów (na Linuxie **AppImage**, na Windowsie **NSIS/MSI**), wspiera **statyczny JSON** i podpisy weryfikowane kluczem publicznym osadzonym w aplikacji. **Nie wyłączaj weryfikacji podpisu i nie przechowuj klucza prywatnego w repo ani binarce**. Klucz prywatny podpisu aktualizacji jest w zatwierdzanym środowisku GitHub Actions Secrets; plan rotacji/backup klucza i recovery po utracie. Manifest desktopu (minimalnie: `version`, `platforms[platform].url`, `signature`) publikuj na stałym HTTPS, pliki pobierania w Releases. Dla różnych wariantów tej samej `linux-aarch64` wybierz jawne osobne cele/manifesty, np. `linux-aarch64-glibc` i `linux-aarch64-musl`, aby **nigdy nie podsunąć użytkownikowi Pixela builda Ubuntu**, i odwrotnie. Podpis Tauri iOS/Android oraz podpisy platformowe nie są tożsame z podpisem desktopowego updatera.

**postmarketOS — szczególny wymóg planistyczny:** w pierwszej kolejności sprawdź **Flathub ARM64 z aktualizacją przez Flatpak**. Opisz dla Pixela: `doas apk add flatpak`, konfigurację Flathub, instalację/aktualizację aplikacji i test trwałego zapisu po zamknięciu/aktualizacji. Zbadaj integrację aktualizacji z Phosh na postmarketOS; nie obiecuj bez weryfikacji cichej aktualizacji w tle. **Tylko jeśli Flatpak nie przejdzie testów**, rozpisz lekki, bezserwerowy, podpisany update już sprawdzonej binarki musl (bez `curl | sh`, bez kompilacji na Pixelu). Niezależnie od metody aplikacja nie może usuwać ani unieważniać `pending_changes` w IndexedDB Tauri, a w przyszłym WWW nie może kasować tego SAMEGO IndexedDB Outbox podczas aktualizacji publicznego indeksu.

**Wspólne reguły dla każdego desktopowego targetu:**

1. **GitHub Actions:** tag SemVer / autoryzowany release → testy (w tym CodeceptJS i test 100% treści) → build matrix → test instalacji/upgrade/downgrade recovery na właściwym OS/arch runnerze lub emulatorze → podpisanie → GitHub Release → aktualizacja statycznego manifestu Pages. Nigdy nie publikuj manifestu pokazującego build, który nie istnieje albo nie przeszedł walidacji. Zaproponuj `stable` / opcjonalny `beta` bez sztucznej komplikacji.
2. **Bez utraty danych, bez automatycznych migracji:** wszystkie treści publiczne są w odtwarzalnym **SQLite** i podmieniane w całości po ręcznej zmianie generatora schematu w repo oraz przejściu testów CI. **Tylko niesynchronizowane operacje i konflikty** znajdują się w trwałym **IndexedDB** (ten sam kontrakt i implementacja JS w Tauri oraz przyszłym WWW); updater programu, Flatpak i updater publicznych danych nie mogą ich nadpisywać ani czyścić. **Potwierdzone przez GitHub operacje i ich payload muszą być usunięte z Outboxa**; zdalny cache w RAM/SQLite jest osobny i usuwalny przy aktualizacji. **Żadnych runtime `ALTER TABLE`, `schema_migrations` ani automatycznych konwersji formatu na telefonie/laptopie.** Niekompatybilne `schemaVersion` wymaga zgodnej wersji aplikacji/snapshotu; przy braku zgodności bezpieczny odczyt ostatniej wersji/komunikat, bez utraty niewysłanego Outboxa. Zapisz testy upgrade, rollback i zgodności z niesynchronizowaną notatką.
3. **Spójność w wielu instancjach:** updater programu nie może przerwać **transakcyjnego zapisu IndexedDB Outbox** ani podmiany publicznego SQLite w środku operacji. W Tauri sprawdź dwie instancje, różne okna, lock/generation/lease synchronizacji, restart i ponowne otwarcie. Zamknij aktywne uchwyty publicznej SQLite przed atomic swap. Przy błędzie aktualizacji zachowaj poprzednią wykonywalną wersję i nienaruszony Outbox. W WWW nowe pliki HTML/JS z Pages wymagają spójnego wersjonowania assetów, manifestu treści i strategii cache; nie aktualizuj kodu w starym JS bez kompatybilności schematu SQLite.
4. **Bezpieczeństwo:** pobieranie HTTPS, klucze podpisujące w GitHub Actions secrets, pinning tożsamości update/signing public key, walidacja wersji/targetu i sum przed instalacją. Nie ufaj samemu SHA-256 z niepodpisanego manifestu, jeśli atakujący mógłby zmienić oba. Bez sekretów i prywatnych danych w Releases, Pages, logach i artefaktach; dla `Notes` mechanizm synchronizacji pozostaje oddzielny od systemu update programu.
5. **Rozdzielenie wersji:** zmiana treści wersetów/tagów → tylko nowy zweryfikowany snapshot danych na Pages/Releases; zmiana JS/Rust → nowy release programu. W manifestach: `appVersion`, `publicSchemaVersion`, `publicContentVersion`, `minAppVersion` oraz opcjonalny `outboxEnvelopeVersion`; NIE wymagaj `userSchemaVersion` ani bazy użytkownika wymagającej migracji SQL. Wersja WWW podlega publikacji statycznej, nie instalatorowi; witryna nie może wyświetlać niekompletnego HTML podczas deployu.
6. **Wynik dla użytkownika i PR:** w zakładce „Aplikacja” pokaż zgodne z jego systemem pliki do pobrania, wersję i changelog, status aktualizacji i link „Pobierz ręcznie”. PR/release ma zawierać proste zdanie „Windows/Linux Mint/X13s/Pixel: aktualizacja X→Y; notatki offline zachowane”; testy i screenshoty udowadniają ten efekt. Zdefiniuj CodeceptJS executable specs w stylu `I.checkForAppUpdate()`, `I.installAvailableUpdate()` (w driverze natywnym), `I.haveAnOfflineNote()`, `I.seeNoteAfterUpdate()` oraz stubs manifestów, podpisów i awarii sieci. Tam, gdzie realne testy instalatora nie są technicznie możliwe przez sam CodeceptJS, wykonaj obok niskopoziomowy test OS w Actions, ale wynik raportuj pod tym samym prostym wymaganiem.

**Ważne:** nie utożsamiaj samoczynnego pobrania nowej treści biblijnej (snapshot SQLite) z aktualizacją zainstalowanego programu. Oba mechanizmy opisz i zweryfikuj osobno, z osobnymi przyciskami/stanami tylko jeśli ma to sens dla UX. Nie planuj własnego procesu aktualizującego iOS/Android z pominięciem sklepów po ich oficjalnej publikacji.

## 9. Testy według Dave’a Farleya: Executable Specifications → DSL → Protocol Drivers → SUT

**Wszystkie docelowe testy akceptacyjne UI/E2E mają być napisane w CodeceptJS i zwykłym JavaScript.** Nie Playwright Test jako osobny równoległy framework testów. CodeceptJS może używać Playwright, WebDriver, Appium itd. **pod spodem jako Protocol Drivers**. Inne narzędzia są dopuszczalne wyłącznie do unit tests, analizy bezpieczeństwa, testów kontraktowych bazy i budowania systemu (nie do pisania drugiej, konkurencyjnej biblioteki scenariuszy E2E).

Zastosuj dosłownie czterowarstwowe podejście Dave’a Farleya (ATDD):

1. **Executable Specifications (Test Cases)** — scenariusze w języku użytkownika i domeny KDZJ, precyzyjnie opisujące **CO** ma działać, bez selektorów CSS, kliknięć i HTTP statusów.
2. **DSL** — wspólny słownik domenowy: `otworzWerset`, `porownajPrzeklady`, `pokazGreke`, `wyszukajSlowo`, `przelaczKarte`, `zalogujPrzezGitHub`, `sprawdzJednoPrywatneRepoNotes`, `utworzPrywatnaNotatke`, `zapiszNotatkeOffline`, `zamknijIPrzywrocAplikacje`, `wznowSynchronizacje`, `zmienTagWspolny`, `przyznajUprawnienieTestowe`, `odbierzUprawnienieTestowe`, `odswiezUprawnienia`, `sprawdzBrakUprawnien`, `zrobZdjecieEkranu`, `poczekajNaIndeks`. DSL usuwa przypadkowe szczegóły platformy.
3. **Protocol Drivers i Stubs** — osobne implementacje interakcji przez Chromium/Firefox/WebKit, natywny Tauri/okna/Appium/WebDriver, GitHub REST i kontrolowane stuby odpowiedzi GitHub (uprawnienia, 401, 403, 409, offline, rate limit). Tu wolno używać locatorów, opóźnień, HTTP i platformowych narzędzi.
4. **System Under Test** — prawdziwa, spakowana aplikacja lub prawdziwy statyczny build WWW, uruchamiane w CI możliwie tak jak w produkcji, nie fikcyjny mock UI.

**Pokaż w dokumentacji co najmniej trzy kompletne scenariusze CodeceptJS** (tylko jako **przykłady kodu w Markdown**, w tym PR nie twórz jeszcze plików testowych), jeden kod DSL oraz dwa szkielety Protocol Drivers. Scenariusze mają wyglądać na przykład tak — bez selectors/`I.click()` w test case:

```js
Feature('Niezależne karty podczas studiowania Biblii');

Scenario('Mogę porównywać różne fragmenty w trzech kartach', async ({ studium }) => {
  await studium.otworzFragmentWKolejnejKarcie('J', 1, 1);
  await studium.otworzFragmentWKolejnejKarcie('1Kor', 11, 10);
  await studium.otworzSlownikGreckiWKolejnejKarcie('λόγος');
  await studium.sprawdzNiezaleznoscOtwartegoMaterialu();
  await studium.zrobZdjeciaTrzechKart('trzy-niezalezne-karty');
});
```

**Wymagane dodatkowe Executable Specifications dla logowania, prywatnych notatek i praw dostępu (opisane prostą polszczyzną):**

- **Tauri:** „Loguję się raz i moje prywatne `Notes` powstaje bez ręcznej konfiguracji”; kolejnych logowań i trzech urządzeń nie wolno zwielokrotnić repo.
- **Tauri:** „Zapisuję notatkę bez internetu, zamykam aplikację, ponownie ją otwieram, a po powrocie internetu ta sama notatka automatycznie trafia do `Notes`”; przy ewentualnej późniejszej wersji WWW z bezserwerowym auth testuj też trwałość po zamknięciu całej przeglądarki.
- **Tauri:** „Pracuję nad notatkami jednocześnie w kilku oknach/instancjach i na drugim urządzeniu; nie tracę edycji przy konflikcie”. **WWW read-only:** „Mam trzy karty z różnymi wersetami; żadna nie przejmuje stanu innej i każda poprawnie czyta wspólną bazę”.
- **Tauri:** „Administrator dodaje mi prawo zapisu do repo aplikacji; po odświeżeniu mogę edytować tagi”; „administrator odbiera prawo; po odświeżeniu już nie mogę, a stary przycisk nie dokona skutecznego zapisu”. **WWW read-only:** „Nie widzę przycisków edycji, nawet jeśli jestem współautorem na GitHubie”.
- „Moje `Notes` są publiczne albo niedostępne — aplikacja nie publikuje żadnej prywatnej notatki, nie tworzy `Notes-2` i pokazuje zrozumiały problem”.
- „Kiedy odłączam konto lub przełączam konto GitHub, nie widzę notatek poprzedniej osoby i nie tracę lokalnych zmian”.

Wymagaj scenariusza CodeceptJS w stylu `I.saveNoteOffline()`, `I.seePendingChanges(1)`, `I.restoreInternet()`, `I.seeNoteOnGitHubStub()`, `I.seePendingChanges(0)`; osobny test sterownika potwierdza brak opublikowanego Markdown/payloadu w trwałym pliku Tauri lub IndexedDB, także po restarcie i zmianie wersji. Wymagaj screenshotów **Tauri**: logowania, GitHub App consent/install (o ile w CI można użyć bezpiecznego fake), lokalnych notatek, oczekiwania na synchronizację, konfliktu, sukcesu, ról i zmiany uprawnień. Dla **WWW read-only** obowiązkowo screenshots publicznych SEO stron (z JS i bez JS), zakładki „Aplikacja”, różnych fragmentów na kilku kartach i **braku UI edycji/logowania**. Nie dołączaj do screenshotów prawdziwych tokenów, danych prywatnych ani rzeczywistych ekranu zgody użytkownika produkcyjnego. Wszystkie standardowe PR testy mogą korzystać ze stubów GitHub, natomiast weryfikację uprawnień i CORS uwzględnij w osobnym, kontrolowanym eksperymencie.

Ustal stabilne fixture/dane testowe, brak sztywnego `sleep`, deterministyczne godziny i fonty, izolację testów, powtarzalne resetowanie indeksu/testowej notatki, uruchamianie po buildzie w prawdziwej przeglądarce i natywnym shellu. Zadbaj o bezpieczeństwo: stubuj **zapis** do zewnętrznego GitHub przy zwykłych PR-ach, nie zapisuj do prawdziwych prywatnych repo użytkowników w CI; oddziel krótkie testy autoryzacji sandbox/test-organization, tylko przy świadomie dozwolonych sekretach.

**Macierz wymagań/testów z 4 poziomami pewności:**

- PR: szybkie unit/contract + CodeceptJS WWW Chromium/Firefox/WebKit + screenshot diff + smoke najważniejszych natywnych buildów.
- Merge/main: pełne CodeceptJS, multi-tab i multi-window, prawdziwe dane i offline/online, budowanie wszystkich wykonalnych targetów.
- Release: podpisane pliki + hash, test instalacji gdzie dostępne VM/emulator i CodeceptJS, zgodność wersji i download links.
- Rzeczywisty fizyczny sprzęt: Pixel postmarketOS (Phosh/Alpine musl) i np. Android/iPhone; **nie udawaj**, że runner GitHub Actions jest fizycznym Pixel 3a XL. Osobna checklista manualnej walidacji czy opcjonalna zewnętrzna farma urządzeń, jeżeli koszt dopuszczony. Wynik fizyczny oznacz jako „wymaga potwierdzenia”, a nie zielony automat.

### Screenshoty: obowiązkowy artefakt KAŻDEJ zmiany UI

- CodeceptJS ma robić pełne i fragmentowe screenshoty na kluczowych trasach/stanach (verse, chapter, porównanie, greka, słownik modal, tag, ojcowie, notatki, logowanie, uprawnienia, pobrania, błąd/offline, multi-tab). Telefon (np. 393×852 CSS px), tablet, desktop (np. 1365×768), jasny i ciemny motyw tam gdzie wspierany, ważne systemy WebView. Gdzie realnie możliwe: screenshot natywnego okna iOS simulator/Android emulator/Linux Tauri/Windows.

### 9.1. OBOWIĄZKOWY pełny test poprawności WSZYSTKICH danych z archiwum ZIP — docelowo <=60 sekund

**To jest nowy, odrębny i obowiązkowy rodzaj testu: test danych, NIE test widoków.** Nie wolno nim zastępować CodeceptJS ani odwrotnie. Zaprojektuj w repozytorium **wersjonowany, śledzony przez Git plik ZIP w katalogu testów**, np. `tests/data/golden-content-v1.zip`, zawierający kompletną, wcześniej zatwierdzoną referencję oczekiwanej treści: **każdy jeden werset każdego obecnego źródła/przekładu**, plus komplet Pism Ojców, publiczne tagi i przypisania fragmentów, wszystkie wystąpienia interlinearu/słownika/Strong i inne rodzaje rekordów, które finalnie trafiają do bazy. Przygotuj mapę: `input/{TNP,UBG,KJV,TR,Fathers,GreekPolish}`, `tags/*.md` oraz inne rzeczywiste źródła → referencyjny ZIP → docelowe tabele SQLite → treści HTML. Nie zakładaj, że aktualne `docs_fts` POC zawiera wszystko, co jest potrzebne do odtworzenia strony, np. strukturę interlinearu, gramatykę, opisy tagów: **osobno weryfikuj pełne dane źródłowe i osobno FTS**. Zapisz literalnie nazwy tabel i kluczy po tym, jak Codex zaprojektuje rzeczywisty schemat.

Proponowane wnętrze ZIP (zwykłe dane, bez screenshotów, tokenów ani prywatnych notatek):

```text
tests/data/golden-content-v1.zip
  manifest.json           # zatwierdzone SHA-256 plików, liczby rekordów, schema, daty źródeł
  verses.jsonl            # wszystkie (translation,book,chapter,verse,text), bez utraty Unicode
  fathers.jsonl           # każdy autor/dzieło/rozdział/ustęp i treść
  interlinear.jsonl       # wszystkie tokeny/odmiany/kody gramatyczne/przypisania
  dictionary.jsonl        # Strong, lemmas, formy, glosy; to, co naprawdę jest w źródłach
  tags.jsonl              # definicje, opisy, przypisania; także zakresy po rozwinięciu
  navigation.jsonl        # księgi, zakresy rozdziałów, występowanie wersetów per przekład
```

Nazwy i formaty są przykładowe; zaproponuj **najprostszy deterministyczny** format dostosowany do rzeczywistych źródeł. Kanoniczne sortowanie, jawna obsługa duplikatów i braków (np. TNP ma 47 ksiąg, KJV/UBG 66; to **nie** jest powód, by „dopisać” brakujące wersety). Treści porównuj jako rzeczywiste wartości z jednoznacznie zdefiniowaną polityką Unicode/końca linii; oddziel znormalizowane tokeny FTS od oryginalnego wyświetlanego tekstu. Nie testuj wyłącznie liczby 115 317 — **100% zgodności kluczy i wartości** tam, gdzie jest zamierzona zgodność literalna. Wyszukuj brakujące, nadmiarowe, podmienione, niepoprawnie przypisane wersety, tagi i formy oraz uszkodzone indeksy. Każda referencja ma wskazywać prawidłową księgę, rozdział, werset, przekład i źródło.

**Test nie może sam sobie wystawiać świadectwa.** Nie generuj i nie zatwierdzaj automatycznie „golden” ZIP z **tego samego właśnie testowanego skryptu**, a następnie nie porównuj skryptu z własnym wynikiem. Archiwum referencyjne powstaje jako **oddzielnie audytowany, jawnie zatwierdzony snapshot** źródeł lub wynik niezależnego eksportera i jest PR-owany oraz reviewowany osobno. Jeśli zmienia się tłumaczenie, poprawia dane albo dodaje legalnie nowe źródło, zmiana referencji ZIP wymaga świadomej, opisanej aktualizacji w tym samym lub odrębnym PR: ludzko czytelny diff referencji (`added/removed/changed`) z przykładami i wskazaniem przyczyny. **Brak samoczynnego nadpisywania baseline**, brak masowego „update snapshots” bez review. Nie dopuszczaj do błędnych testów przy zmianie oczekiwanych danych, ale nigdy nie akceptuj pominiętych wersetów przez jednoczesne pomniejszenie oczekiwań.

**Weryfikacja szybka, bez renderowania 31 000 widoków**: po zbudowaniu artefaktu SQLite w GitHub Actions osobny job/skrypt czyta ZIP strumieniowo i porównuje go z bazą po kluczach/hashingach (np. `python3` ze standardowej biblioteki: `zipfile`, `sqlite3`, `hashlib`; bez ciężkich zależności) albo bezpośrednio z kanonicznym eksportem danych generowanym z bazy. Może używać `EXCEPT`, indeksów, agregacji i SHA-256 per rekord/zbiór; nie może pomijać rekordów ani polegać wyłącznie na 10 próbnych zapytaniach. Sprawdź `PRAGMA quick_check`, `FTS5 integrity-check` oraz spójność relacyjnego schematu i wyników eksportu; unikaj kosztownego `integrity_check` przy każdym PR, jeśli przekracza limit — to może zostać w pełnym, nocnym sprawdzaniu. Benchmarkuj koszt sprawdzenia pełnych danych na prawdziwym korpusie.

**Twardy cel czasowy: 60 sekund na sam kompletny test danych, na hostowanym GitHub Actions runnerze, z plikami wejściowymi już przygotowanymi.** Mierz wall-clock, włącz watchdog/timeout, dokumentuj wynik i liczbę porównanych rekordów; nie rozciągaj limitu przez ukryte wielominutowe próbkowanie. Generowanie danych/SQLite to odrębny krok builda, który należy usprawnić i cache'ować; jeśli w praktyce test danych ze wszystkimi rekordami przekracza minutę, opracuj szybszy deterministyczny algorytm, a dopiero potem opisz uczciwie bloker z pomiarami. Nie zakładaj, że cały wieloplatformowy build Tauri i screenshoty skończą się w 60 sekund — **ten limit dotyczy pełnej kontroli danych**.

**Zawsze uruchamiaj na każdym PR i ponownie na każdym merge/push do `master`/`main`**, także gdy zmiana dotyczy generatora, importera, schematu, normalizacji, manifestu, publikacji Pages albo kodu aplikacji. Nie pozwól, by nowy publikowany snapshot trafił do Pages/Releases bez zielonego testu. Zakoduj warunek bramkowy w workflow; brak ZIP/SQLite/wyników nie jest „pomijanym testem”. Zaplanuj dodatni test diagnostyczny „usunięty jeden werset → błąd zawiera referencję”, analogicznie „podmieniono treść jednego wersetu”, „zniknął tag”, „formę grecką przypisano do złej referencji”, „zaktualizowano legalnie źródło i baseline → przechodzi po review”.

**Raport testu zrozumiały w PR:** `Sprawdzono 100% wersetów, form, tagów i ustępów Ojców · 0 brakujących · 0 nadmiarowych · 0 zmienionych · czas 18,2 s` (czas tylko jako przykładowy format, **nie rzeczywisty pomiar**). Przy błędzie pokaż typ danych, łączną liczbę różnic oraz do np. 20 konkretnych kluczy i odczytów **bez naruszania praw do cytowania**. Udostępnij artefakt JSON/Markdown ze szczegółowym diffem; w PR i check summary umieść proste podsumowanie, tak żeby autor nie musiał czytać logów. Zip referencyjny pozostaje w `tests/data/` repozytorium i jest wersjonowany, ale musi mieć legalnie publikowalną treść — najpierw zinwentaryzuj licencje i uprawnienia do ponownej dystrybucji poszczególnych źródeł. Jeśli danych nie wolno umieścić publicznie w ZIP, zaprojektuj jawny, równie rygorystyczny test hashy/odcisków per rekord bez publikowania chronionego tekstu i nazwij to wyraźnie wyjątkiem, nie pomijaj po cichu takich danych.

**Wymagany dokumentacyjny output:** format ZIP+manifest, sposób niezależnego zatwierdzania golden snapshot, dokładny algorytm/SQL porównania, skrypt i lokalizacja (proponowane, nie twórz teraz), pipeline trigger/gating, macierz wykrywanych regresji, krótki kosztorys czasowy, kryterium `<=60 s`, przykład raportu PR i jawna lista źródeł/testowanych pól. Zaproponuj też szybki test zgodności zbioru wygenerowanych statycznych URL ze zbiorem referencji z ZIP, aby 100% wersetów miało stronę wtedy, gdy wdrożony zostanie per-verse SEO.

## 10. Całość CI/CD w GitHub Actions, nigdy na laptopie użytkownika

**Żadnego obowiązku lokalnego budowania, testowania, instalowania toolchainów czy generowania baz na ThinkPadzie/Linux Mint**. Laptop użytkownika nie jest runnerem. Wszystkie buildy, testy automatyczne, snapshoty, statyczny hosting i release wykonują **GitHub Actions (hosted runners)**. Lokalny telefon/komputer służy jedynie jako urządzenie docelowe do korzystania z aplikacji i okazjonalnej ręcznej walidacji hardware’u, jeśli nie można jej wykonać na GitHub Actions.

Zaprojektuj niewielką liczbę czytelnych workflow: (a) PR/test/visual + **zawsze pełny, <=60-sekundowy test danych z zatwierdzonego ZIP**, (b) build matrix w tym Flatpak/Flathub x86_64/aarch64 z lintem manifestu i smoke testem bez własnego runnera, (c) podpisane desktopowe release z updaterem Tauri dla instalatorów NSIS i AppImage, integracją aktualizacji Flathub i sklepami Android/iOS (fallback musl tylko gdy Flatpak nie przejdzie prób), (d) generacja statycznych stron wersetów i deploy GitHub Pages. Cache kompilacji, niezależne joby, zależności, fail-fast dla krytycznych testów, szybka odpowiedź na PR, raportowanie tego, czego nie udało się sprawdzić. **CI musi sprawdzać parytet PL+EN wszystkich stringów UI, pomocy, SEO, Flathub AppStream oraz repozytoryjnych metadanych Google Play/Apple App Store; lokalizowane screenshoty mają być aktualizowane i recenzowane przy zmianie UI.** Nie uruchamiaj sekretów w nieufnych PR/forkach, ustaw minimalne `permissions`, ogranicz concurrency. Dla iOS/Android/Windows plan kluczy i podpisów z GitHub Actions secrets/environments i zatwierdzanym release; brak sekretów w logach, JS, screenshotach i artefaktach.

**Deploy:** wyłącznie poprawnie zweryfikowana gałąź/tag, manifest SHA, atomowe publikowanie nowej wersji, kontrola `latest`, rollback manifestu, linki w zakładce „Aplikacja” wskazujące pliki istniejące i publicznie pobieralne. Zablokuj publikację, gdy build/test wymaganej platformy się nie powiódł; różnicuj targety fakultatywne i krytyczne, nie ogłaszaj niekompletnego release jako kompletnego.

**PR w prostym języku, bez technicznego żargonu jako jedynej dokumentacji:**

```markdown
## Co zmienia się dla czytelnika?
...
## Dlaczego to robimy?
...
## Jak to sprawdziłem?
... (CodeceptJS + GitHub Actions, link)
## Przed / Po
| Przed | Po |
|---|---|
| screenshot | screenshot |
## Co jeszcze nie działa / ryzyka?
...
## Czy zmiana wymaga nowej wersji lub migracji danych?
...
```

Zadbaj, żeby CI publikował podsumowanie zrozumiałe bez czytania surowych logów. Zamierzony screenshot diff jest **powodem do review**, nie automatycznie „green”. Przyszłe PR-y mają być małe i łatwe do obejrzenia. Każda funkcja ma definicję sukcesu w kategoriach użytkownika, nie implementacji.

## 11. Etapy migracji: zaprojektuj dokładną kolejność i kontrolowane usuwanie legacy

Plan ma zawierać tabelę kolejnych małych PR-ów, dla każdego: priorytet, zależności, zmiany, testy, screenshots, ryzyka, akceptacja, rollback i sposób demonstracji. Uwzględnij co najmniej:

1. Udokumentowanie funkcjonalności legacy + checklistę parytetu i baseline screenshotów istniejącej wersji.
1a. **Już przy tworzeniu nowego frontendowego szkieletu:** wspólne katalogi i18n `pl/en`, przełącznik języka UI, niezależne preferencje `annotationLayers`, lokalizacje SEO/store listings i testy tłumaczeń; nie odkładaj lokalizacji „na koniec”.
2. Kanoniczny schemat SQLite i deterministyczny generator/manifest w CI (treści, tagi, interlinear, ojcowie, FTS, licencje), testy parytetu z legacy; **audytowany ZIP w `tests/data/` zawierający wszystkie rekordy, kontrola 100% kluczy+wartości z docelową bazą SQLite w <=60 s, uruchamiana na PR i merge/main**.
3. Minimalny wspólny frontend JS/Unpoly i router z pełnymi deep-linkami w WWW i Tauri; **jeden wspólny renderer w JS** używany również przez generator statycznych HTML w Actions. **Przybliżona próba 1 000 rzeczywistych wersetów, szacunek 31 tys. kanonicznych stron, weryfikacja limitów 1 GB/10 min Pages i pełne sitemap**. W kolejnych małych PR-ach wykonaj całą generację dopiero po udowodnieniu jej wykonalności.
4. Dwa adaptery **publicznego SQLite** (browser WASM i Tauri native) i jeden wspólny **IndexedDB Outbox JS**; kontrakty/fixture testy; multi-tab Web Locks/SAH Pool dla publicznych danych + multi-instance Tauri SQLite i IndexedDB.
5. Przekłady i czytnik wersetów oraz porównanie, nawigacja, zakładki i niezależne karty.
6. Greka/słownik/gramatyka/modal i zgodność z obecnym `GreekInterlinearService` i danymi Strong.
7. Pisma Ojców i tagi read-only, zakresy oraz odniesienia.
8. Prywatne notatki Markdown `.md` w `<login>/Notes` + JEDEN IndexedDB Outbox (TYLKO szkice, niepotwierdzone operacje i konflikty) w Tauri oraz ewentualnym writable WWW; potwierdzone notatki tylko GitHub/RAM/usuwalny cache; atomowy zapis, izolacja kont, eksport, wiele okien, automatyczna synchronizacja po następnym uruchomieniu i konflikty przy ręcznej edycji Markdown na GitHub. WWW read-only pozostaje bez prywatnych danych.
9. **GitHub auth bez backendu + REST API:** Tauri: GitHub App Device Flow, automatyczne utworzenie/podłączenie dokładnie jednego prywatnego `Notes`, REST API zamiast Git CLI, ten sam trwały IndexedDB Outbox JS tylko dla niesynchronizowanych zmian (bez pliku JSON i bez migracji publicznego SQLite), przyszłe WWW writable — IndexedDB na ten sam format oraz odświeżanie praw. WWW: analiza realności bezserwerowego auth, a jeśli nie udowodniona — **definitywna docelowa decyzja read-only SEO**, bez loginu, bez backendu i bez czekania na zgodę właściciela. Żadnego brokera, także serverless. W osobnym podetapie zaplanuj usunięcie runtime klona i `git fetch/add/commit/push` z obecnego kontenera.
10. Edycja współdzielonych tagów **w Tauri** przez uprawnionych użytkowników GitHub, **egzekwowanie cofnięcia praw przez GitHub API przy zapisie i odświeżanie UI po zmianach uprawnień**, aktualizowanie snapshotu przez GitHub Actions. W WWW read-only nowe tagi pojawiają się po opublikowaniu statycznej wersji; edycji tam nie ma.
11. Pełne CodeceptJS acceptance tests, DSL, Protocol Drivers, visual regression i raporty PR (narastająco już od pierwszego PR, a nie dopiero na końcu).
12. Workflow matrix: GitHub Pages + **Flathub/Flatpak x86_64 i aarch64** (preferowane także dla postmarketOS) + opcjonalne samodzielne AppImage Mint/X13s z updaterem Tauri + Windows x86_64/ARM64 z updaterem Tauri + Android/iOS z podpisem/sklepami + dotychczasowy fallback binarki Alpine musl, jeśli Flathub nie przejdzie testów. **Upgrade 1→2 bez utraty niewysłanych notatek w IndexedDB Tauri / przyszłym WWW; cache po aktualizacji wolno odtworzyć, bez migracji publicznego SQL.**
13. Publiczna zakładka „Aplikacja” z prawdziwymi bezpośrednimi pobraniami z Releases i czytelną informacją o aktualizacjach; **stały config głównego repo i stabilny manifest aktualizacji odporny na rename publicznego repo**.
14. Dwutorowe testy parytetu / canary migracji, bezpieczeństwo, wydajność, backup/rollback, go/no-go.
15. **Dopiero po spełnieniu kryteriów**: decommission ASP.NET Core/Redis/Podman/Cloudflare runtime oraz **usunięcie całego POC** i niepotrzebnych benchmarkowych elementów z produktu. Nie pozostawiaj dwóch UI ani dwóch technologii renderowania w końcowym produkcie.

Wykryj rzeczywiste istniejące funkcje, które nie zostały wyliczone powyżej. Dla każdej pokaż „gdzie jest teraz / gdzie będzie / jak przetestujemy / czy wymaga konta / czy offline”. Specyficzne prawa do przekładów i słowników muszą być zachowane wraz z atrybucją. Nie przyjmuj, że każdy zestaw danych ma licencję pozwalającą na dowolną redystrybucję i pakowanie do instalatora — zinwentaryzuj licencje i ewentualne ograniczenia.

## 12. Wymagane artefakty i format odpowiedzi

Dokumentacyjny PR ma zawierać **konkrety**:

- Podsumowanie obecnych komponentów i możliwości (tabela parytetu).
- Jeden rekomendowany diagram architektury (Mermaid), plus przepływy **odczyt wersetu**, **wiele kart**, **aktualizacja snapshotu**, **edycja wspólnego taga**, **prywatna notatka offline → GitHub**, **OAuth** — w Mermaid lub równie czytelnej formie.
- Proponowane **kontrakty adapterów JS** (sygnatury i przykładowe obiekty, bez implementacji); jedna struktura SQLite i przepływ generowania z istniejących źródeł.
- Docelowy płaski układ katalogów i tabelę mapowania legacy → target.
- Konkretną macierz OS/architektura/runtime/WebView/pakiet/build runner/test driver/test screenshot/podpis/release/stan blokad.
- Autoryzację GitHub **w Tauri**: UX od kliknięcia „Zaloguj” do automatycznego prywatnego `<login>/Notes` z **edytowalnymi ręcznie na GitHubie plikami Markdown `.md`**, uprawnienia GitHub App, JEDEN trwały Outbox IndexedDB JS w Tauri / przyszłym WWW writable tylko z niepotwierdzonymi operacjami (pusty po pełnym sync), konflikt po edycji `.md` na GitHub i dynamiczne przyznawanie/odbieranie write do publicznego repo; **WWW read-only pod SEO jako zatwierdzony fallback** i warunki, które *ewentualnie* umożliwiłyby bezserwerowy login WWW. Żadnych dodatkowych usług OAuth, żadnego kosztu utrzymywania backendu. Konkretną mapę **Git CLI z serwera → GitHub REST API w JS** oraz testy konfliktów i uprawnień.
- Macierz testów CodeceptJS i przykładowe Executable Specifications + DSL + Protocol Drivers/Stubs; standard baseline/screenshot review. **Osobne testy SEO bez JS i osobny pełny test referencyjnego ZIP ↔ SQLite w <=60 sekund — nie mylić ich z E2E.**
- Plan **wymienialnego, tylko publicznego SQLite** oraz **jednego wspólnego IndexedDB Outbox w JS dla Tauri i przyszłego WWW writable**, **tylko z niesynchronizowanymi payloadami i konfliktami**, bez stałego cache notatek, z transakcjami, eksportem i leasingiem między oknami; osobny, wymienialny cache Markdown w RAM lub SQLite; **bez runtime migracji schematu**. Odróżnienie od `window.localStorage`, plus test restartu/upgrade/offline.
- Wykonalny, szczegółowy **plan aktualizacji Windows (Tauri updater), Linux Mint/X13s (Flathub albo AppImage + Tauri updater), Pixel postmarketOS (Flathub `aarch64` jako preferowana ścieżka, natywne musl tylko fallback), Android/iOS (sklepy po publikacji)**: podpisy, pakiety, manifesty, instalacja/rollback, CI, test Flatpak na realnym Pixelu, trwałość IndexedDB Outbox i podmiana całego publicznego SQLite, bez runtime migracji.
- Projekt **konfiguracji repozytorium przez jeden parametr**/wygenerowany `app-config.json` i scenariusz rename/transfer GitHub repo, bez hardkodowanych adresów, wraz z zachowaniem identyfikatora `Notes` i stabilności URL Pages/updatera.
- Pełny plan etapowych, małych PR-ów, zależności i kryteriów `go/no-go`, w tym usunięcie POC po migracji. **Wynik analizy wykonalności osobnego HTML dla każdego wersetu na GitHub Pages oraz projekt golden ZIP/testów danych z raportami PR i czasowym budżetem.**
- Listę decyzji już potwierdzonych eksperymentami vs. ryzyk do walidacji vs. funkcji niemożliwych bez zewnętrznego komponentu lub dodatkowych opłat. **Nie proponuj własnego serwera jako fallbacku**: jeśli WWW potrzebowałoby serwera do zapisu, ma zostać read-only.
- Dla każdego ryzyka: konsekwencja, minimalny weryfikowalny eksperyment **w przyszłym PR**, kryterium sukcesu i możliwy fallback; **nie realizuj tych eksperymentów teraz**, jeżeli wymagają kodu.
- Krótkie podsumowanie całego PR prostą polszczyzną z tym, co plan umożliwi użytkownikowi, i co jeszcze wymaga decyzji.

**Wymóg PL+EN:** osobny rozdział `i18n-and-store-listings.md` w dokumentacyjnym PR, kryteria kompletności tłumaczeń z każdego przyszłego PR, gotowe do rozbudowy UI, niezależność tekstów/glos od języka UI, SEO `hreflang`, metadane i screenshoty sklepów oraz testy CodeceptJS dla obu języków. **Nie implementuj niczego poza planem i dokumentacją.** Nie usuwaj żadnego kodu w tym zadaniu. Nie twórz od razu całej infrastruktury testowej ani publicznego release. Powołuj się na konkretne pliki repo i oficjalne źródła, wyjaśniaj założenia i nie obiecuj niemożliwych rzeczy (zwłaszcza bezserwerowego OAuth w WWW, realnych limitów GitHub API i publicznej instalacji iOS bez podpisów). Po zakończeniu utwórz **dokumentacyjny PR** z czytelnym, nietechnicznym opisem, zweryfikuj, że jest otwarty i skierowany do `master`, podaj URL. **Bez merge i bez deployu.**
